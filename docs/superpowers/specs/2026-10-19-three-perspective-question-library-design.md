# 三方并列的双语题库：任务规范

日期：2026-10-19  
状态：待审阅  
来源：用户提供的 Interview Compass 诊断与 GPT goal prompt；开工前以当前仓库和主分支复核。

## 目标

把 Interview Compass 建设成候选人、面试官、管理者三方并列的双语参考题库。读者应能从自己的任务进入少量经过逐题复核的核心题，看到这道题要判断什么、可以观察什么证据、可以怎样继续追问，以及不同质量表现如何区分。其余内容继续保留并明确标为扩展内容。

内容表达的是可参考的判断框架，不提供标准答案、自动评分或招聘结论。保持内容克制，不扩展成完整案例库，也不新增泛化的“适用边界”章节。

## 已确认决策与约束

- 候选人、面试官、管理者是并列受众。
- 目标核心库为 100–150 个双语题目 ID；按候选人准备、面试官取证、管理者评估与带团队三个主要站点受众分别收录 30–50 个。核心题逐题复核，未复核内容保留为扩展题。
- 核心题的内容规格：一个考察意图、3–4 条可观察信号、2–3 条本题专属追问、一句弱回答表现、四档逐题锚点。中英文成对并保持条数和语义对应。
- 核心题候选清单须先交用户审阅。未获清单审阅前，不得开始改写任何核心题。
- 保持现有 questionId 和公开 URL；不删除扩展题，不编造来源或事实，不写标准答案。
- 各阶段独立 PR，只开 PR、不合并、不直接推 main。每阶段用中文报告 PR、改动、遗留问题和需要决策的事项。
- 可把无须用户决策的工程阶段继续完成；候选题内容改写必须在候选清单通过后另行执行。

## 内容与数据契约

### Perspective

新增必填枚举 `perspective: candidate | interviewer | manager`，表达题目由谁回答/执行，独立于将题目带给读者的主要站点受众，也不表达问题属于哪个能力域。中英文同一 ID 必须一致。已有题通过确定性迁移规则给出初始值，同时生成低置信/人工确认清单；无法可靠判定的内容不得伪装成人工审核结果。核心库的三方数量按经批准的主要站点受众清单统计，不把题目 perspective 迁移值作为读者入口分组。

迁移前必须对抽样和冲突规则做审阅。可以先用规则推断作为数据补全，但应能区分推断状态与已复核状态，以免把自动分类包装成事实。记录字段使用 `perspectiveReview: inferred | reviewed`；现存题迁移为 `inferred`，只有人工逐题核对后才可改为 `reviewed`。迁移重跑时重新计算仍标记为 `inferred` 的记录；人工标记为 `reviewed` 的记录不得被覆盖。不要把含“你”的语法或场景标签简单等同于某一视角。

### Quality tier

新增 `qualityTier: core | extended`。既有题默认 `extended`；只有通过候选清单审阅和逐题内容审核的题才标为 `core`。core/extended 中英文必须一致。阶段 A 不能提前挑选或改写核心题。

### Core 内容字段

- `weakAnswer`：核心题必填，描述常见的弱证据表现，不写羞辱性标签或答案模板。
- `anchors`：核心题必填，四档分别对应 `notPassing`、`passing`、`excellent`、`exceptional`，每档为本题专属的可观察区分点。若直接复用现有逐题分析数据，必须核对含义，不得仅因字段名相同就迁移。
- 旧有 `question-specific-analyses.json` 保持向后兼容；是否把它的某些内容逐题迁到新结构，由实现计划规定安全且可回滚的迁移策略。
- 核心题 `intent` 写一个判断目标；中文建议以“判断回答者能否……”表达，英文采用 “Assess whether the respondent can …” 的等义表达。语言风格允许自然变化，不把固定前缀当作唯一正确文案。
- 核心题 `signals` 为 3–4 条具体、可观察的证据线索。
- 核心题 `followUps` 为 2–3 条与题目场景紧密相关、深度递进的追问。
- 中英文的核心题 signals、followUps 和 anchors 条数一致，语义对应；intent 与 weakAnswer 也须双语等价。
- 标签只表达真实适用范围。核心题 `careerTracks` 和 `responsibilityScopes` 各最多 2 个；筛选/场景入口需由核心题实际分布支撑。

## 分阶段交付

### A. Schema、迁移和质量报告（独立 PR）

新增字段和核心题条件校验；迁移脚本为全部现存题补 perspective 和 extended；报告推断不确定项与标签分布。把逐题分析的现状和兼容方案写清。extended 的内容质量违规先告警，不把全库旧数据变更成硬失败；结构损坏、无效枚举、双语字段冲突仍按 schema 错误处理。运行内容检查、类型检查、单测和构建；E2E 是否必要由计划按受影响功能确定。

### B. 双语内容规范（独立 PR）

新增 `docs/content-style-guide.md`，以中英文说明 intent、signals、followUps、weakAnswer、anchors、perspective、标签纪律和双语一致性。正反例须引用现有、经核实的内容，避免摘录过长或把历史判断表述成当前事实。

### C. 核心候选清单（独立 PR，审阅闸门）

新增 `docs/core-question-candidates.md`，提出 100–150 个稳定 ID，列出 perspective、能力域、入选理由，以及双语现况/风险。覆盖八个能力域并尽量平衡三种 perspective；优先审查现有精选题单、12 个已有专属分析题和确有访问需求的场景题。候选题须具备可具体化的判断目标和证据。清单 PR 完成后等待用户审阅。此 PR 和之后的筛选讨论都不能改写候选题内容或标记为 core。

### D. 核心题内容分批（每批 20–30 个 ID，一个 PR）

仅在用户审阅候选清单后开始。逐题修订中英文题干、意图、信号、追问、弱回答、锚点及必要标签，标记 `core`。修复确认存在的合并残留追问、失配追问和命名漂移，但不擅自改变 ID/URL；无法安全处理的在 PR 中列明。每个 PR 列出 ID 和 perspective，并为 2–3 题展示简短改前改后理由。

### E. 导航和详情体验（1–2 个独立 PR）

- 首页首屏提供三个并列入口：准备面试/晋升、面试他人、评估/带团队；各入口在一至两次点击内到达对应核心题。
- 场景页优先呈现匹配的核心精选题单；晋升场景链接“晋升对话”。扩展题保留并清楚标记为未逐题复核。
- 详情页按 perspective 调整内容顺序；候选人突出意图、信号、自评锚点，面试官突出追问、weakAnswer 和锚点，管理者突出证据和反馈。共同信息可复用，不创建三套重复内容。
- 延续单题页的相近题、所属题单、下一题入口；搜索直达详情也能看到有效后续阅读入口。
- 指南作为可选入口，统一显示名称。增加双语 hreflang；本次不改批次 ID URL。
- 验收 390px 和 768px 布局；若仓库当前浏览器测试工具可用，保存截图并附 PR 描述。

## 全局验收

1. 最终核心题总量在 100–150 ID；三类主要站点受众各 30–50 ID；题目 perspective 逐题复核、双语一致，但不要求按回答者类型凑足数量；所有题双语配对且通过严格 core 检查。
2. 每条核心题均有专属 intent、signals、followUps、weakAnswer、四档 anchors；英语与中文条目语义和数量对应。
3. extended 内容及稳定 ID/URL 保留；extended 的质量问题可见但不阻塞全站构建。
4. 三条首页入口可快速到达相应核心题；搜索进入的详情至少有三种有效下一步入口。
5. 质量校验输出能指出失败记录和字段；迁移可重复运行且可追溯，不静默覆盖人工编辑。
6. 每个 PR 构建通过，按影响范围运行内容校验、单测和 E2E；PR 保持未合并。

## 本任务执行规则

把本规范作为新的待执行任务规则。按 A → B → C → 用户审阅 → D → E 的依赖顺序交付；A、B、C 和展示改动可在各自边界内推进。核心内容改写在 C 的用户审阅完成前一律暂停。所有阶段只创建 reviewable PR，不合并，不直接推 `main`。如果核对发现规范与真实数据/既有接口冲突，先保留稳定 ID、来源和现有内容，以报告说明，再将必要决策集中反馈，不凭空扩充功能范围。
