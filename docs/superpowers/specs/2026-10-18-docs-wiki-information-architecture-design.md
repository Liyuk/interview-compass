# 文档型 Wiki：站点结构与多级阅读设计

日期：2026-10-18。状态：V2设计修订稿，尚未实施。

本设计继续《站内资源与体验V2设计》，根据用户补充的“doc网站、wiki、文章多级目录”明确站点形态。资源与功能盘点仍有效；后续实施以本文的文档结构和阅读层级为依据，统一发现流程作为其中一个能力。

## 1. 产品形态

Interview Compass 定位为面向工程师的文档型知识库。题目是核心知识条目，方法解释如何使用题目，能力和阶段提供理解框架，题单和路径组织一次具体准备任务。

首页帮助选择入口；进入内容后，使用稳定的文档阅读框架。用户可以按目录系统浏览，也可以通过关键词、知识关联或外部链接跳入任意位置。

成功标准：读者知道“我在什么位置、上层是什么、这一页讲什么、当前读到哪节、还能去哪里”。页面层级、文章章节与知识关系都有真实内容依据。

## 2. 三种导航结构

| 结构 | 表达什么 | 放在哪里 | 规则 |
| --- | --- | --- | --- |
| 文档树 | 本文属于哪个栏目、有哪些上级与同组页面 | 左侧 | 以编辑确定的归属为主；通常展开到3层，必要时4层 |
| 文章目录 | 当前文章的章节与子章节 | 右侧/手机正文上方 | 默认收录H2/H3；H4仅在确实帮助定位时加入 |
| Wiki关联 | 概念、题目、方法、阶段之间的关系 | 正文链接与文末关系区 | 明确关系类型，支持反向引用；同标签推荐单独标注 |

面包屑只表达一个稳定的主要归属；“从哪个结果/题单进入”作为阅读来源单独保留。主要归属不随搜索来源变动。分类维度可以交叉，但不因此制造多个互相矛盾的父节点。

保留现有六个全站入口及旧URL。左侧目录按当前板块展示必要分支，同时保留切换整个知识库的入口。

树中的“开始使用”等是从现有手册与方法内容重组出的建议章节，尚未作为新文章发布。首版优先复用现有内容，不为空栏目批量生成占位页。

题目数量较多，不把1,334题全部列进全站侧栏。能力叶子页、题库结果和题单承载题目列表；单题侧栏显示所属能力路径，或“当前题单”模式下的有序短列表。两种模式名称清楚，不能把题单临时顺序当作题目的永久归属。

“按岗位浏览”是分类视角，“按岗位与阶段阅读”是责任要求。目录和引导文字解释各自用途，搜索结果也标识类型。

## 4. 文档与知识条目模型

统一使用稳定contentId表达内容身份，标题、语言、路径分别管理。保留现有questionId，避免为每种视角复制题目。

内容类型：guide（说明）、method（方法）、concept（知识概念）、question（问题）、collection（精选集合）、path（任务或专题路径）、stage-reference（阶段参考）。

- 页面树节点：id、类型、标题、目标路由、children、排序、是否可折叠；分组节点可以没有可点击文章。
- 文章元数据：contentId、locale、title、description、primaryParentId、所属板块、对应翻译、显式关联、复核信息。
- 章节节点：anchorId、标题、level、children；它们属于文章，不作为独立文档父子关系。
- 关系边：源、目标、关系类型、简短理由；可选contrast用于对比题。

新增概念文章必须有可维护的真实说明。已有能力叶子可以先作为概念入口，展示边界和题目；不把每个主题标签都自动包装成百科文章。

## 5. 页面框架

宽屏示意：

```text
品牌｜六个全站入口                 搜索｜准备目标｜语言
───────────────────────────────────────────────────
文档目录       首页 / 能力地图 / 系统设计     本页目录
▾ 能力地图     系统设计                     问题与范围
  ▾ A专业能力  本页用途与内容类型           关键概念
    计算机基础 ─────────────────            ▸ 容量估算
    系统设计   文章正文                     ▸ 故障假设
    AI工程     H2 / H3 内容                 实践问题
               …                           相关资料
               关联知识 / 被哪些页面引用
               上一篇       下一篇
```

- 全站页头保持紧凑、稳定；准备目标是可选的阅读条件，浮层不推动正文。
- 左侧目录保留当前分支展开状态，只展开当前祖先和用户主动展开的分支。展开按钮与跳转链接分开，支持键盘和当前项状态。
- 中间标题区包括面包屑、文章标题、短摘要和真实类型/复核标记。正文保持可读行宽，参考表格有明确横向滚动区域。
- 右侧目录显示当前章节，锚点链接可复制；滚动时更新可见章节状态，不频繁修改浏览器历史。
- 普通文章使用“上一篇/下一篇”；题单阅读使用“上一题/下一题”。跨分类的同类题只作为关联，不假称编辑阅读顺序。
- 短页面和搜索结果无需右侧目录，不预留空列；操作页拥有更宽结果区域。

手机：全站导航使用一个菜单；内容标题附近提供“文档目录”抽屉和“本页目录”折叠区，分别命名。页面加载时直接呈现最终折叠状态。文档抽屉打开后可定位当前页，支持Escape、关闭与焦点返回；文章目录展开属于明确用户操作，不自动展开占满首屏。

初期目录不会固定挤压正文；若采用吸顶，只让当前上下文控件保持可达，并处理锚点偏移。200%缩放和长英文也必须可读。

## 6. 文章多级目录

一个H1为文章标题；H2代表实质章节；H3表达章节内部主题；H4默认不进入目录。跳级标题在构建期报告，列表项、卡片标题、表格标题和操作按钮不自动纳入目录。

示例：

```text
H1 系统设计题如何阅读
  H2 明确问题与约束
    H3 功能范围
    H3 容量与时延
  H2 比较方案
    H3 数据一致性
    H3 故障与恢复
  H2 需要哪些证据
  H2 相关问题与资料
```

右侧目录应保留以上父子关系，不能把五个H3都压成与H2同级。默认显示H2与当前H2下的H3，用户可展开其他章节；短目录可全部展开。

所有可定位标题有稳定且唯一的anchorId。内容标题改名后保留旧锚点别名；中英文使用明确的章节对应关系。语言切换找不到对应小节时落到对应页面顶部并保留页面语义，不将中文hash机械拼到英文页面。

Markdown/MDX从渲染后的标题树生成目录；结构化Astro页面由同一份章节描述同时生成正文标题和目录。目录不能再由另一份手工数组维护，否则标题、可选区块与锚点容易漂移。

现有 `WikiOutlineItem {id,label}` 需要扩展为带level或children的章节树；普通页面与Starlight适配为同一OutlineNode契约，实际页面只渲染一份目录。

## 7. Wiki关联与反向链接

从现有显式relatedQuestions与分类关联逐步建立以下关系：

| 关系 | 页面表达 | 来源 |
| --- | --- | --- |
| 解释/前置概念 | 阅读这题前可了解什么 | 编辑声明 |
| 应用/实践问题 | 这个概念可以用哪些问题检视 | 编辑声明或已确认分类关系 |
| 对比 | 两题比较什么、差异在哪 | 现有relation/contrast，扩展到文章 |
| 使用方法 | 用哪套方法提问、核查证据 | 编辑声明 |
| 收录于题单 | 哪些精选集合使用这道题 | 构建时根据集合ID引用反推 |
| 引用本文 | 哪些文章明确链接到这里 | 构建时从显式关系生成反向索引 |
| 同类内容 | 同能力或主题下还有什么 | 标签/分类推导，并明确标注推荐依据 |

反向链接无需后台：构建期从全部内容关系计算，输出页面数据或小型索引。不能把同标签内容全部标为“引用本文”。循环关系可以存在，但页面树不能有环。

首版无需全屏关系图。优先让正文概念链接、文末关系区和反向引用可用。未来要画图时必须基于同一真实关系数据，而不是装饰性图谱。

## 8. 搜索与文档结构统一

全站搜索覆盖说明、方法、概念、阶段、题单与题目；结果标识类型、所属板块、标题和命中章节。支持“全部 / 文档与方法 / 题目”范围。

准备目标仅筛选题目及可确定适用范围的题目集合，通用说明、方法与阶段资料始终可查。现有pagefindFilters会为整个查询附加profile过滤，因此需要改为分类型查询或统一合并结果，不能把同一过滤器直接套在全知识库上。

搜到文档中的某个章节时可直达锚点；搜题时能继续使用分类筛选。结果为空时允许切换范围、清除条件、查看匹配栏目；不同类型之间的混合排序要有可说明的分组或相关性策略。

文档树是浏览结构，搜索是跨结构入口，两者共享contentId和路由表。

## 9. 与现有内容的落地映射

- 手册：现有9个H2先整理层级；“开始使用/阅读一题/使用约定”形成可独立维护的组。长章节有真实需求时再拆文章。
- 方法：现有面试官、候选人、反问、晋升内容形成方法栏目，H3实质步骤进入多级目录；重复卡片标题不全收。
- 能力地图：现有8域、47叶子是天然知识树；叶子补齐目的、边界和相关题目入口，专属概念说明逐步补写。
- 阶段：共用模型、岗位模型、维度、外部映射成为明确的参考文档分组。岗位阶段摘要作为入口，49个折叠区块的总览拆解为可阅读的同组页面。
- 题目：问题、意图、信号与追问先读；阶段比较和AI工具按需打开。12道专属分析与其余共用框架保持真实区分。
- 题单与路径：提供有目的的阅读顺序，与知识树并存；岗位尽调保留指南类型。

既有URL和锚点建立兼容清单。需要拆分旧长文时，原页保留为总览/兼容入口，旧锚点继续有解释和新位置链接；可以从同一内容源生成兼容片段，避免维护两份正文。不以一次改版破坏已有题目分享链接。

## 10. 推荐实现

沿用Astro数据页和Starlight文档渲染，两者接入同一个DocsShell及导航契约。结构化题目保留现有schema；真正的说明、方法和新概念长文逐步采用MDX。

新增/统一的职责：

1. ContentRegistry：稳定ID、类型、语言、路由、标题、所属文档节点。
2. NavigationTree：文档父子、排序、可折叠状态；由registry和编辑目录声明生成。
3. OutlineTree：章节与子章节、锚点、可选章节条件；正文与目录共享来源。
4. RelationIndex：显式关系、题单收录和反向引用；与标签推荐分开。
5. ReadingContext：当前来源集合、位置和前后篇；不改变永久文档归属。
6. SearchAdapter：按内容类型查询、合并、目标适用过滤与章节直达。

ContentRegistry用于统一当前routes/site-navigation/page-presentation/wiki-navigation中的共同声明，但不要把所有内容规则塞进一个超大模块。

构建期校验：页面树无环、节点可达、父节点存在、ID与URL唯一、语言对应完整或声明缺失、章节ID唯一、标题层级有效、显式引用目标存在、上一篇/下一篇顺序可解释。资源和许可检查继续保留。

## 11. 本版范围与实施顺序

本版应完整实现：左侧多级文档树、右侧H2/H3文章目录、面包屑、文章前后导航、明确类型和复核状态、正文关联与构建期反向链接、跨类型搜索及移动端对应交互。

本次题单在阅读上下文形成后接入；笔记、在线编辑、讨论、账户和自动评分不纳入本版。

顺序：

1. 固化内容注册表和真实目录声明，映射已有页面并列出空缺内容。
2. 用手册、方法、能力叶子各一篇验证统一DocsShell与多级目录。
3. 接入其余知识页面、阶段参考和结构化题目，调整正文层级。
4. 建关系/反向链接与集合内前后阅读。
5. 接入按类型搜索与统一筛选，补齐请求失败、空态、无脚本与存储受限降级。
6. 全站检查、双语/锚点兼容与桌面/移动验收后更新PR。

## 12. 验收场景

- 在系统设计题直接落地：知道所属能力、能向上到系统设计知识页，再进入同组问题。
- 在方法长文：左侧切同组文章，右侧区分H2/H3，复制小节链接后重新打开准确定位。
- 题目有显式概念/方法关联：能进入关联文章，并从“引用本文”找到这道题。
- 当前来自精选题单：前后题按编辑顺序走；面包屑依旧表示题目的永久知识归属。
- 已选择客户端高级阶段：搜索“使用说明”仍能找到手册；搜索题目可以按目标缩小范围。
- 中英文互切：对应页面、目录和可映射章节正确；旧链接、旧锚点仍有可理解落点。
- 小屏进入长文：文档树与本页目录默认收起，正文立即可读，导航展开不触发意外布局跳动。
- 目录/索引/阶段数据加载失败：核心内容仍可读，工具有真实重试或明确降级。

本轮交付为上述完整设计修订及与现有内容的映射，不声称新的文档树、多级文章目录和Wiki反向引用已经实现。
