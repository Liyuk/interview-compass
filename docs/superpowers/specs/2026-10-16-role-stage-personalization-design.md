# 岗位阶段模型与全站个性化设计

日期：2026-10-16

状态：设计稿，待用户审阅；尚未实现。

## 1. 目标与已确认约束

用户首次进入站点时选择岗位类型和目标阶段，之后只看到适用于该组合的题目。右上角持续显示当前选择，可重新选择，也可切换到全部题目。先补齐各岗位阶段模型，再上线个性化。

已确认：

- 严格过滤，不采用匹配题目优先、其他题目继续混排的方式。
- 所有现有岗位都必须有可解释的阶段模型，不能把工程阶段强套给产品、运营等岗位。
- 默认中英文双语，站点仍是提供问题、考察意图与证据判断框架的工具。
- 不恢复站内长表单练习；已有外部 AI 提问按钮保留。

本设计采用职业轨道共用阶段定义、岗位分别映射能力要求的方案。阶段表示目标责任，不是当前能力测评、工作年限或公司职级换算。

## 2. 现状与缺口

实际检查的实现：

- `src/lib/taxonomy.ts` 有 12 个岗位，以及 4 条粗粒度职业轨道。
- `src/lib/capability-model.ts` 只支持初级、中级、高级、资深工程师，以及工程管理者、管理管理者。
- `src/lib/capability-expectations.ts` 已提供 A–H 责任深度及文字证据锚点。
- `src/lib/question-catalog.ts` 按岗位、职业轨道等标签取交集，但没有具体目标阶段字段。
- 普通页面与 Starlight 使用说明共用站点页眉；即时搜索与完整搜索各自调用 Pagefind，需要同时接入偏好。

关键缺口不是缺少弹窗，而是题目适用阶段缺少明确依据。现有阶段引用的能力集合只能用于辅助内容标注，不能直接视为每道题的阶段适用结论。

## 3. 岗位与轨道模型

### 3.1 岗位映射

保留现有岗位 ID 与公开链接。新增模型归属，不为本次功能重命名岗位。

| 模型族 | 现有岗位 | 复用与区分 |
| --- | --- | --- |
| 工程 | engineering、frontend、backend、mobile、ai-engineer | 共用责任阶段；专业实践、作品证据及风险关注按子岗位分别定义 |
| 数据 | data | 使用数据工作通用责任描述；分析、工程、建模案例需保留适用条件 |
| 产品 | product | 以问题发现、产品判断、结果验证及产品组合责任递进 |
| 运营 | operations | 以执行闭环、运营策略、持续运行及多业务运营机制递进 |
| 市场与增长 | marketing | 以市场研究、渠道/实验、增长体系及市场组合判断递进 |
| 设计 | design | 以设计交付、研究与验证、复杂体验及跨产品体验机制递进 |
| 项目管理 | pmo | 以项目协调、独立交付、复杂项目群及项目组合治理递进 |
| 管理 | manager | 提供通用一线管理与管理管理者模型；不默认具有工程专业背景 |

共用阶段定义不等于共用专业要求。前端、后端、客户端和 AI 工程至少分别提供专业实践范围、hands-on 证据和关键风险说明。数据岗位暂不拆出新的导航岗位；每条标准明确其适用的数据工作情境。

### 3.2 阶段名称草案

以下是本站的编辑性责任参照，不声称对应任何公司的正式职级。IC 表示专业贡献路径，不要求直属下属。

| 模型族 | IC 1 | IC 2 | IC 3 | IC 4 | 一线管理 | 管理管理者 |
| --- | --- | --- | --- | --- | --- | --- |
| 工程 | 初级工程师 | 中级工程师 | 高级工程师 | 资深工程师 | 工程管理者 | 管理管理者 |
| 数据 | 初级数据专业人员 | 数据专业人员 | 高级数据专业人员 | 资深数据专家 | 数据团队管理者 | 数据组织管理者 |
| 产品 | 初级产品经理 | 产品经理 | 高级产品经理 | 资深产品专家 | 产品团队管理者 | 产品组织管理者 |
| 运营 | 初级运营专员 | 运营专员 | 高级运营专业人员 | 资深运营专家 | 运营团队管理者 | 运营组织管理者 |
| 市场与增长 | 初级市场专业人员 | 市场与增长专业人员 | 高级市场与增长专业人员 | 资深市场与增长专家 | 市场与增长团队管理者 | 市场与增长组织管理者 |
| 设计 | 初级设计师 | 设计师 | 高级设计师 | 资深设计专家 | 设计团队管理者 | 设计组织管理者 |
| 项目管理 | 项目协调者 | 项目经理 | 高级项目/项目群经理 | 项目组合治理专家 | 项目管理团队管理者 | 项目管理组织管理者 |
| 管理 | 不提供 IC 阶段 | 不提供 IC 阶段 | 不提供 IC 阶段 | 不提供 IC 阶段 | 一线管理者 | 管理管理者 |

管理岗选择只显示两种管理阶段。其他岗位同时提供专业与管理两条路径；在选项中分组，不用一条从初级直通管理管理者的晋升阶梯暗示唯一发展方向。

现有六个工程阶段 ID 与 URL 保持有效；新增模型使用带模型族前缀的稳定 ID。现有 `executive` 题目标签保留用于全部题库浏览，不凭这个标签增加未建立责任标准的高管目标阶段，也不将其自动归入管理管理者。首轮阶段范围到管理管理者。

### 3.3 共用责任递进

| 阶段 | 主要责任 | 证据要求 | 人才组织责任 |
| --- | --- | --- | --- |
| IC 1 | 在明确目标、指导与边界下解决限定问题 | 说清本人操作、检查与求助过程 | 不设通用人员管理要求 |
| IC 2 | 独立承担常见任务或模块，可靠闭环 | 对比方案、交付结果、识别异常并升级 | 岗位适用时支持同伴，不要求考核人员 |
| IC 3 | 处理复杂或模糊问题，协调相关方 | 约束、方案取舍、验证与可迁移复盘 | 可带教、评审和帮助他人独立承担工作 |
| IC 4 | 对关键专业领域及跨团队实践负责 | 领域突破、持续采用、可归因结果与适用边界 | 培养专业负责人，不以直属团队为必要条件 |
| 一线管理 | 对团队结果和人才机制负责 | 招聘、授权、绩效、发展、容量与交付证据 | 对本人授权范围内团队人才建设完整负责 |
| 管理管理者 | 通过管理者经营多团队及组织能力 | 组织设计、业务组合、管理质量、继任和系统性改进 | 培养与校准管理者，建设组织机制 |

高级 IC 可以拥有很强的技术/专业规划责任，但不因此默认拥有绩效管理、预算或招聘决策权限。管理者的专业要求是做出可靠判断和授权，不按个人操作量单调递增。

### 3.4 岗位差异的具体落点

每个岗位阶段沿用现有四维组织：业务结果、领域专业、团队影响、人的竞争优势；每维 3–5 条标准。每条标准包含行为要求、可核验的证据、适用条件和 A–H 能力引用。

岗位区别不能只替换名称。例如：

| 岗位 | 独立承担阶段 | 复杂责任阶段 | 关键领域阶段 |
| --- | --- | --- | --- |
| 工程 | 实现并验证模块；处理失败路径与运行问题 | 权衡系统方案，推进复杂变更，验证可靠性与业务作用 | 主导领域架构及演进机制，降低多团队长期成本 |
| 数据 | 明确粒度/口径，完成可复现分析或管线并检查质量 | 处理偏差、因果边界、模型/数据变化及跨方口径冲突 | 建立可复用数据方法和治理机制，验证决策/生产收益 |
| 产品 | 独立澄清用户问题，验证方案并跟踪结果 | 对比竞品或历史基线，协调约束，验证复杂产品决策 | 对产品领域方向、机会组合和持续验证机制负责 |
| 运营 | 独立执行策略，检查指标与异常并闭环 | 解释人群、触点、流程差异，设计实验并纠偏 | 建立可持续运营体系，控制复制成本与结果衰减 |
| 市场与增长 | 研究目标群体，执行渠道或实验，解释指标口径 | 比较渠道与定位，识别增量、归因及投入取舍 | 对市场机会组合、增长机制和长期经济性负责 |
| 设计 | 完成有依据的设计并验证可用性 | 在多角色、多流程约束下做研究、方案对比与验证 | 改善跨产品体验与研究/设计机制，论证用户和业务作用 |
| 项目管理 | 明确承诺、依赖、风险，推进独立项目交付 | 协调复杂项目群，处理优先级冲突与交付变更 | 建设组合治理和资源决策机制，验证治理成本与效用 |

所有阶段都体现以下站点观点，但证据尺度随岗位和责任变化：

- 充分了解上下文；比较多个合理方案，不要求固定数量的解法。
- 有竞品/行业数据时检查可比性；缺少时使用自身历史或相似情境，并说明差异。
- 因果、个人贡献和 hands-on 必须有具体过程或产物佐证；不能把团队结果全部归给个人。
- 学习、自驱、思维、韧性通过事件与变化体现，不作人格诊断。
- 亮点需要客观基线、挑战、个人判断与结果；岗位适配包括双方诉求、工作方式和文化匹配。

沿用 A–H 责任深度图及逐项文字锚点。新增岗位须给出自己的要求，不能复制工程岗数值。百分比是编辑性责任深度，不是掌握率；它既不直接决定题目是否匹配，也不替代题目的 1–4 分评分标准。本次不改现有百分比刻度。

## 4. 题目阶段适用数据

新增岗位—阶段组合表，独立于题目中英文正文，例如 `src/content/question-applicability.json`，以稳定 questionId 为键。每项包含明确的组合、理由和审核状态：

```json
{
  "questionId": "a-ai-engineering-eval-set-design",
  "reviewStatus": "reviewed",
  "profiles": [
    { "roleId": "ai-engineer", "stageIds": ["mid-level-engineer", "senior-engineer"] }
  ],
  "rationale": "适用性条目结构示例；实际阶段需结合本题约束、责任与证据逐题确认。"
}
```

示例只说明结构，不将这两个阶段视为已审核的内容判断。采用岗位—阶段组合而非两个独立数组，避免“产品初级、工程高级”被错误展开成“产品高级、工程初级”。

每道已发布题都需完成适用性审核，或明确记录为只供全部题库浏览及原因；双语正文共用同一条适用性记录。只有 `reviewed` 组合参与个性化。

审核从现有 roles、careerTracks、responsibilityScopes、能力与题意提出候选组合，再按实际责任、前置知识、上下文和所需证据检查。不能只按题目长度、词汇难度或单个能力标签分阶段。

通用行为题可在多个阶段出现，但题目详情展示对应阶段的证据提醒。例如“失败复盘”在初级阶段关注本人操作和改进，在组织阶段关注重复问题、机制变化与管理者责任。保留题目自身评分锚点，在其上增加阶段适用提醒，不批量生成机械重复的评分正文。

没有可靠适用性结论的题目不自动加入所有阶段。上线前输出岗位×阶段覆盖报告，并审核所有零题组合、只供全部浏览的题目及其理由。题量少时如实显示，不凑数或扩大标签。

## 5. 严格过滤合同

匹配条件：题目已发布、语言匹配，且已审核适用性表明确包含当前岗位—阶段组合。在该集合内，再与页面已有主题、能力、场景、题型等条件取交集。

- 多个已标注阶段采用 OR；岗位与阶段采用组合匹配，不跨组合展开。
- 工程通用题是否适用于前端等子岗位，由明确适用记录决定；不运行时自动扩展父岗位。
- 岗位与阶段匹配是相关性，不是通过判定，不意味着所有匹配题都是该阶段的必考题。
- “查看全部题目”退出个性化过滤，但保留用户选过的岗位与阶段，方便切回。
- 局部“清除筛选”仅清除页面筛选，不悄悄退出当前个人目标。
- URL 显式筛选继续与个人目标取交集；冲突时说明冲突条件，提供清除页面条件或查看全部的动作，不自动切换目标。

一个共享的纯函数负责组合匹配。列表、题量和搜索不能各自维护不同的近似判断。

## 6. 首次进入与切换

首次进入普通页面或使用说明页面，若浏览器没有有效偏好，则展示“选择你的准备目标”对话框：

1. 选择岗位，随后显示该岗位的阶段分组。
2. 每个阶段提供一句责任说明，帮助用户按责任选择，而非猜职级名称。
3. 点击“按此目标浏览”后应用严格过滤；点击“先看全部题目”后进入全部模式。
4. 选择岗位变化时，清除不兼容阶段；未选完整不能提交。

右上角使用现有图标语言显示“前端 · 高级工程师”或“全部题目”。点击打开同一个编辑对话框，包含当前选择、切换目标与查看全部；不表现为需要登录的账户。

对话框支持键盘、焦点圈定、关闭后焦点恢复及可见标签。Escape/关闭视为本次会话暂不设置，保持全部模式；当前会话不再次弹出，下次新会话仍可提示。明确点击“先看全部”则持久记住全部模式。移动端把触发器放在可发现的页眉位置，不把它藏到很深的导航中。

偏好使用带版本号的 localStorage，只保存在当前浏览器，跨语言复用稳定 ID。读取失败、无效/退役 ID 时回到全部模式并允许重新选择；存储不可用时仍可在当前页面内设置，不出现阻断错误。

## 7. 页面行为与信息密度

| 页面 | 个性化后的行为 |
| --- | --- |
| 首页 | 显示目标摘要及匹配题量，目标路径/精选题预览按同一组合过滤 |
| 面试题库 | 默认匹配集合，保留主题等局部筛选；分页基于过滤后题量 |
| 主题、岗位、能力及其叶子页面 | 题目、预览、计数使用匹配集合；零题栏目保留说明与切换全部动作，不显示成坏链接 |
| 使用场景/任务路径 | 保留完整任务说明，题目集合按目标过滤；角色目标与任务身份是不同维度，例如工程师也可作为招聘面试官 |
| 精选集 | 保留人工排序，过滤后如实显示题量；不从全量题库随机补足 |
| 阶段能力 | 当前目标提供快捷定位，仍可主动对比其他岗位/阶段；模型解释不被过滤隐藏 |
| 提问方法、使用说明 | 正文完整保留；其中题目预览及页眉搜索遵循当前目标 |
| 题目详情 | 直接链接始终可读；不匹配时提示“此题不在当前目标范围内”，提供修改目标/全部浏览；相关题只推荐匹配题 |

图表和栏目首次加载时不先短暂闪出全量题目再收缩。HTML 保留可用的静态全部内容；启用 JS 时在偏好解析完成后显示受影响的题目区域，异常时恢复静态内容。导航、正文与阅读路径不能被整个页面加载遮罩阻断。

站点统计区分“题库总量”与“当前目标匹配”，避免将个人筛选数误称本站总题量。切换目标后分页重置到第一页，保留关键词和兼容的页面筛选；结果变化通过 aria-live 简要提示。

## 8. 搜索、链接与持久化

Pagefind 为题目索引明确的 profile token，例如 `frontend:senior-engineer`。即时搜索和搜索页都在检索时按 locale 与 profile token 过滤，再分页或截取；不能先取前几条再隐藏不匹配条目。

个性化模式下搜索返回题目；提问方法、说明、阶段模型等文档保留独立固定入口，避免没有 profile token 的文档全部消失或混入题量。全部模式维持原有搜索范围。

浏览偏好不自动写入每个普通链接。复制题库筛选链接时，显式写入当前 profile 作为该次链接的筛选条件，保证接收者看到相同集合；打开链接不覆盖接收者的长期偏好。页面突出显示“来自链接的目标”，用户可明确采用为默认，或移除链接目标恢复本地偏好。URL 目标优先于本地偏好，但不允许两套目标同时叠加。

语言切换保留 URL 筛选与目标，不改变长期偏好。详情永久链接保持原格式。

## 9. 实现边界与迁移

- 扩展阶段注册表和内容校验，移除验证器硬编码“仅六个阶段”的假设，但保留六个工程阶段及其既有标准。
- 新增岗位模型注册、问题适用性、偏好存取、匹配函数、页面协调器；模块各自承担一个职责。
- 页眉对话框复用现有 Radix Dialog 和站内图标、字体、颜色，不引入新的组件体系或账号依赖。
- 所有题目集合与 Pagefind token 由同一份适用性数据生成；不在浏览器打包完整题面与评分正文来筛题。
- Astro 静态构建与 GitHub Pages 继续使用现有部署方式；不增加服务器或外部 AI 调用。
- 未进入本次范围：新增题目数量目标、恢复站内练习、公司薪酬/职级对照、用户账户、高管模型扩写。

按依赖顺序交付：先阶段模型与适用性数据及覆盖审计，再共用过滤与搜索，最后首次选择和右上角切换。所有岗位模型与题目适用性达到审核门槛前，不开启首次弹窗，避免先发布无法兑现的严格过滤。

## 10. 验收与检查

内容验收：

- 12 个岗位均有有效阶段选项，阶段定义、责任边界、3–5 条/维标准及证据齐全，中英文结构一致。
- 工程子岗位有专门的专业证据要求；其他岗位没有残留工程师/编码模板措辞。
- 每道已发布题有已审核的组合或明确的全部浏览限定理由，不存在未审核组合上线。
- 每个可选择的组合至少有一道已审核题；若不能合理覆盖，则补充适用题或收窄/合并阶段定义并重新审阅，不能发布必然空白的目标选项。
- 报告列出岗位×阶段总数、A–H 覆盖、重复跨阶段比例、仅全部浏览题目及低覆盖点；低覆盖阈值设为少于 10 题，逐项写解释，不能以达到阈值替代质量判断。

逻辑与浏览器验收：

- 测试岗位—阶段组合匹配、跨组合误配、未知 ID、全部模式、URL 目标优先级与局部筛选交集。
- 验证首次进入、明确看全部、临时关闭、刷新、跨页、语言切换、多标签页偏好同步、存储异常及目标切换后的分页。
- 即时搜索、完整搜索、精选集、相关题、首页预览与完整题库对相同组合使用一致集合。
- 验证详情直接访问不匹配题、空关键词、零结果、筛选冲突及清除条件。
- 在桌面与移动端验证键盘、焦点恢复、屏幕阅读标签、视觉闪烁与顶栏空间。
- 运行现有内容校验、单元测试、Astro 类型检查、完整构建/Pagefind 及相关 E2E；工作流沿用项目已有 CI。
