# 问题与考察意图：通用框架、职能框架、责任范围如何组合

研究日期：2026-10-14。定位以用户最新说明为准：这是以大量问题为核心的启发式站点，不提供标准答案；帮助读者知道为什么问、想了解什么能力，以及如何继续追问。

“问题背后要查什么”优先理解为“考察什么”。背景知识、实践方法与阅读来源是可选辅助，不是每道题的主角。本文研究外部设计依据并提出本项目的组织建议，不把站点包装成经过验证的人才测评工具。

## 1. 结论与设计依据

建议采用三个可以分别维护、组合展示的维度：

1. **通用能力**：问题主要帮助了解哪一种判断、行动或理解能力。
2. **职能知识与实践**：这种能力在研发、产品、运营等工作中具体面对什么对象、约束和方法；另有真正专属的技能问题。
3. **责任范围**：是在个人任务、项目、团队、多个团队或组织方向上讨论问题；管理者和高级个人贡献者有不同责任，不混成统一职级顺序。

“通用问题”表示可以跨角色迁移，不表示人人必须回答。岗位框架也不只是给通用题换名词；它需要包含岗位专属知识问题。以下是研究事实和来源，后续章节中的八域映射、字段、题目与追问均为本项目设计建议。

## 2. 一手来源中的事实

### 2.1 Monzo：通用内容和岗位内容实际组合

Monzo 快照的渲染代码按 topic 名称匹配 generic topic，并在对应层次展示通用 criteria 与岗位 criteria；没有匹配的 topic 使用岗位自身的标题和内容。README 则说明岗位文件的组织方式与字段。通用文件包括 knowledge、impact、communication、teamwork、conduct；岗位文件增加研发 mastery、产品 user-centricity / data skills / domain knowledge 等。这是可直接借鉴的“共用概念 + 岗位补充”结构，不需要复制其六级等级或评价标准。[合并渲染代码](https://github.com/monzo/progression-framework/blob/689e6224a1a0b477ac3a1f326f1beef7494a4efa/src/components/renderers/levelledRenderer.js#L168)、[固定 README](https://github.com/monzo/progression-framework/blob/689e6224a1a0b477ac3a1f326f1beef7494a4efa/README.md)、[通用框架](https://github.com/monzo/progression-framework/blob/689e6224a1a0b477ac3a1f326f1beef7494a4efa/frameworks/generic.md)、[产品框架](https://github.com/monzo/progression-framework/blob/689e6224a1a0b477ac3a1f326f1beef7494a4efa/frameworks/product.md)。

其后端框架包含专业实现、影响和领导相关条目；运营领导框架涉及辅导领导者确定优先级、跨领域协作和授权。这说明职能与责任范围是不同变化轴。此处 Monzo operations 主要是银行运营，不能直接当作国内内容、社区、增长、商家运营的完整覆盖。[后端框架](https://github.com/monzo/progression-framework/blob/689e6224a1a0b477ac3a1f326f1beef7494a4efa/frameworks/engineering/backend.md)、[运营领导框架](https://github.com/monzo/progression-framework/blob/689e6224a1a0b477ac3a1f326f1beef7494a4efa/frameworks/operations/ops-leadership.md)。

### 2.2 SFIA：专业技能和通用属性可以独立考虑

SFIA 官方说明区分专业技能与通用属性，并以自主性、影响和复杂性说明责任层次；各维度可分别考虑，再组合成岗位期望。本项目可以借用这种分维度的思路，不必逐字引入 SFIA 七级内容或声称与 SFIA 职级等价。[SFIA 官方说明](https://sfia-online.org/en/about-sfia/how-sfia-works)。

### 2.3 英国岗位框架：角色共享技能，同时保持专业差异

英国官方产品经理框架组织了角色职责、角色层次与具体技能，包括用户洞察、价值、产品结果和优先级；页面也列出共享技能的其他角色。业务分析师框架的业务建模覆盖组织、流程、关系、信息与交互，以及建模对决策的支持。它们支持“同一技能被多角色使用”，也提醒我们把业务模型的语义理解和特定数据库实现分开。它们描述英国政府岗位，不能直接作为中国企业统一要求。[产品经理](https://understand-digital-data-roles-skills.service.gov.uk/role/product-manager/)、[业务分析师](https://understand-digital-data-roles-skills.service.gov.uk/role/business-analyst/)。

### 2.4 Tech Interview Handbook：问题意图与影响范围可以说明清楚

TIH 的行为面试页面按关注方向组织问题，例如主动性、模糊情境、冲突、成长与沟通，同时讨论不同责任范围。它是项目贡献者对实践的总结，不是各大公司的官方统一规则。可以借鉴“题目关联关注方向”的表达；其中回答示例和录用建议不是本项目需要搬入的部分。[固定行为面试页面](https://github.com/yangshun/tech-interview-handbook/blob/e1d28e8886c0b6ff3e50da991ce0e895134ddc59/apps/website/contents/behavioral-interview-rubrics.md)。

### 2.5 PM Interview Project：能力、问题与角色集合分开

PM Project 分别维护 competency model 和 role-loop presets：前者解释问题关注哪些能力和观察方向，后者按增长、平台、AI 产品等岗位选择问题，还区分高级个人贡献者和实际管理他人的角色。本项目适合借鉴这几个内容实体的关系。其评分、压力设置和面试流程不属于当前站点需要。该仓库仍是公开试用参考，不能据此声称测评有效性。[能力模型](https://github.com/deanpeters/The-Product-Manager-Interview-Project/blob/5bce351728eda31470d3737d98b22679ba87fc78/docs/competency-model.md)、[角色集合](https://github.com/deanpeters/The-Product-Manager-Interview-Project/blob/5bce351728eda31470d3737d98b22679ba87fc78/docs/role-loop-presets.md)。

### 2.6 OPM：问题可以围绕工作相关能力设计

OPM 说明结构化面试通过过去行为或假设情境了解工作相关能力，同时包含统一问题和评分要求。本项目只借鉴“从工作相关能力倒推问题”的关系。开放探索的问题站没有执行其标准化施测与评分，因此不能称作完整的结构化招聘测评。[OPM 官方说明](https://www.opm.gov/policy-data-oversight/assessment-and-selection/structured-interviews/)。

## 3. 本项目建议：保留八域，补足问题与框架的关系

已有八域可以继续作为通用分类，但每题应该指向更具体的子能力。不能只贴“判断力”“沟通能力”这样过宽的标签。

| 通用能力域 | 可以用于问题意图的具体方向 |
|---|---|
| A 专业解题与实现 | 理解原理、问题拆解、抽象、方案约束与权衡、实现与验证 |
| B 业务理解与领域建模 | 业务语义、规则和状态、领域边界、商业与数据关系 |
| C 价值判断与方向规划 | 判断目标、识别机会、优先级、机会成本、规划与调整 |
| D 交付执行与持续运营 | 依赖、资源、风险、推进与反馈、持续改善 |
| E 协作沟通与影响 | 理解分歧、表达理由、达成协作、影响与协调 |
| F 人才与组织建设 | 授权、培养、组织机制、管理者发展 |
| G 学习适应与持续成长 | 修正认识、迁移学习、反馈后的变化、失败后的恢复 |
| H 职业责任与工作方式 | 责任边界、风险透明、专业诚信、工作习惯与互相期待 |

这是组织内容的框架，不要求每个岗位覆盖同样比例、不要求每题观察全部能力，也不通过一道题推断人的固定性格或潜力。

### 3.1 职能框架包含两类内容

**通用能力在岗位中的具体表达**：例如优先级在研发中可能涉及故障、需求、技术债；产品中涉及用户问题、机会与路线图；运营中涉及渠道、人群、活动和资源。

**真正的岗位专属能力**：例如并发语义、编译原理、数据库索引；产品研究方法、需求验证；增长实验设计、渠道归因、社区规则。为它们单独编问题，不强行写成“你怎么思考”的通用题。

领域建模跨职能，但关注对象有差异：产品关注用户关系和业务规则；研发关注规则如何正确映射状态、接口和存储；运营关注人群、权益、活动与执行规则。商业化既可能是 B 的计费和结算规则，也可能是 C 的定价策略选择，按主问目的分类。

### 3.2 责任范围作为独立维度

可标记个人任务、项目、团队、多团队、组织方向。另标记个人贡献者、管理者、管理管理者。不要把“多团队”自动等同二线管理：高级工程师也可能通过专业影响协调多团队；二线管理的专属点是管理者发展、组织结构与运行机制。

校招生可用课程、社团、实习情境来探索同样方向，不要求实际承担公司级项目。岗位名称和年限不能代替实际责任范围。

## 4. 同一个通用问题在不同角色中如何展开

以下题目是设计说明，不是标准答案或回答样例。

### 4.1 优先级：资源不够时，你如何决定先做什么、暂缓什么？

通用意图：了解如何确定目标、比较代价与收益，以及在信息变化时重新判断。主要方向 C 的优先级与机会成本。

| 角色语境 | 可使用的具体追问 | 关注的判断过程 |
|---|---|---|
| 研发 | 故障治理、新需求、技术债同时出现，你比较哪些约束？ | 业务影响、可靠性风险、依赖与长期维护的比较 |
| 产品 | 多个用户诉求彼此竞争时，你先验证哪一个？ | 问题的重要性、证据质量、机会成本与阶段目标 |
| 运营 | 同一预算可投渠道、活动或留存动作，你如何取舍？ | 人群差异、增量与自然变化、投入产出和副作用 |
| 一线管理 | 两项工作都要求同一关键成员时，你如何分配？ | 容量、依赖、授权、培养与承诺的协调 |
| 二线管理 | 多个团队各有合理优先事项时，如何形成共同方向？ | 组合取舍、决策权限、跨团队机制与调整条件 |

若重点改为“排期、协调依赖、跟进风险”，主方向转为 D；若重点改为“如何建立可持续的资源决策机制”，转为 F。保留共同主题，不把不同主问硬塞成同一问题。

### 4.2 失败：回顾一次没有达到目标的事情，当时的判断后来如何改变？

通用意图：了解如何区分事实、假设、外部变化与自身行动，并据反馈修正做法。主要方向 G 的反思与适应。

- 研发：原先相信的性能、规模或架构假设是什么？什么观测改变了认识？
- 产品：需求没有成立，还是交付后未产生预期价值？如何区分？
- 运营：结果变化来自动作，还是季节、其他渠道或样本差异？
- 一线管理：个人补救是否变成团队的实际改进？
- 二线管理：如何发现跨团队重复出现的模式？是否调整了运行机制？

这些追问引导事实和思考，不暗示“坚持”或“停止”永远正确。若要了解风险是否如实披露，另关联 H 的问题。

### 4.3 领域模型：你如何知道大家说的“订单完成”是同一件事？

通用意图：了解能否识别概念含混、建立规则和边界；主要方向 B 的语义与模型。

- 产品：下单、支付、履约、售后分别对应什么状态与用户承诺？
- 研发：状态、事件、接口、存储是否保持同一语义？规则变化如何映射？
- 运营：活动统计、权益发放、退款后的指标如何使用这些定义？
- 一线管理：如何促成团队共享定义，发现实现与业务规则的不一致？
- 二线管理：不同业务线是否应该拥有各自定义？共用边界由谁维护？

数据库建模、机器学习特征口径、商业结算可以成为相关专属问题，不要求每位读者在同一题展开全部内容。

## 5. 问题页：解释为什么问，不给预设结论

正文优先，考察意图紧随其后；后续内容按需要展开。

| 字段 | 作用 | 要求 |
|---|---|---|
| 问题 | 一个能独立理解的主问 | 必须 |
| 为什么问 / 考察意图 | 解释这题希望了解什么具体能力 | 必须，尽量一两句话 |
| 主要能力与适用主题 | 内容归类和跳转 | 最小必要元数据 |
| 观察方向 | 提醒关注解释中的哪些过程、事实或区别 | 可选，不写高低分或录用门槛 |
| 继续追问 | 澄清概念、补充约束、比较选择、检验变化 | 可选，按实际价值添加 |
| 角色 / 范围差异 | 同一问题在不同工作语境中的变化 | 可选，不必列所有岗位 |
| 背景知识与实践 | 需要理解的概念、方法及一手阅读来源 | 可选，不当成必读清单 |
| 相关问题 | 相邻、深入、对比、其他角色语境 | 可选，注明关联理由 |
| 来源与维护 | 原创 / 参考 / 改编、链接、日期 | 内部维护必需，页面适量展示 |

“观察方向”例如写“关注他如何区分当时已知的信息和事后解释，以及什么信息会改变选择”。不要写“必须使用某框架才算优秀”或“回答出三项即可通过”。它提供关注点，保留多种合理做法。

知识题也可解释意图。例如“事务隔离解决什么问题？”可以关注并发异常、概念边界和选型约束；链接权威数据库文档供深入阅读。不要为保持无答案而把客观知识包装成不存在正确性的开放讨论。

## 6. 大量问题的内容维护与入口

建议保存问题、能力说明、角色框架三个独立内容类型。能力页解释概念并列出相关问题；角色页集合通用题、岗位语境与专属题；问题只有一份主记录，角色变体引用它。若主问的能力意图已经改变，拆成新题并建立关联。

无需穷举“每个能力 × 每个岗位 × 每个责任范围”。只有语境或追问确实变化时才补变体。岗位框架可以是一张能力与专业主题的组合地图，不能称为对所有岗位通用的完整招聘标准。

读者可从“我想思考的问题”“我关注的能力”“我的职能角色”进入同一问题集合。筛选可包括责任范围、问题类型和场景。问题类型区分知识理解、过去经历、假设情境、方案设计和开放反思，防止将不同形式混为一种。

整理既有题目时优先补清楚考察意图。若只能写“考察综合能力”，需要收窄主问或保留为开放反思题；若能说明知识主题但不能可靠推断工作表现，就只说明知识目的。题目数量可以很大，说明仍可以很短。

## 7. 边界与尚未验证的地方

- 上述外部项目支持内容组合的设计，不证明本项目能准确测量能力或预测绩效。
- 本文不生成答案、分数、录用判定，也不要求回答样例或建立标准化面试流程。
- 启发式探索可自由选题；企业正式招聘如何使用，应由实际工作需求决定，站点不替组织制定标准。
- 来源中的等级、公司价值观与文化条目属于其语境。H 应展示职业责任、工作方式和相互期待，避免把与面试官相似当作文化匹配。
- 本地快照均保留原许可。这里只记录结构性研究和原创设计建议，不复制 PM Project 的题卡正文；公开内容改编另核对归属与许可。
- 本次只写研究文档，没有实现元数据模型、题目迁移或站点功能。
