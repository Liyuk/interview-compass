# 面试与晋升知识库：公开框架调研

研究日期：2026-10-14。用途：为本仓库规划能力体系、题目模板、评价规则与分层路径提供依据。仅记录第一手公开来源的必要摘要，不抓取全文。下文「事实」表示来源明确公开的做法；「建议」是面向本仓库的设计判断，不代表来源机构的招聘制度，也不是通用职级标准。

## 1. 结构化面试：先定义能力，再收集可评分证据

**事实。** OPM将结构化面试定义为针对岗位能力，系统询问过去行为或假设情境下的行为；所有候选人使用相同预设题目、顺序与评分标准。[OPM：Structured Interviews](https://www.opm.gov/policy-data-oversight/assessment-and-selection/structured-interviews/)

**事实。** Google re:Work的2026年3月版本强调岗位相关问题、完整反馈、统一行为评分标准、面试官训练与校准；能力类别包含岗位知识、问题解决和领导力，避免模糊的文化契合判断。[Google：结构化面试指南](https://rework.withgoogle.com/intl/en/guides/a-guide-to-structured-interviewing-for-better-hiring-practices)

**建议。** 知识库不应只给「参考答案」。每题同时写清能力目标、适用角色、主问题、允许的标准追问、证据要求、行为锚点和常见反例。技术概念题可以检查解释是否正确；项目与管理题应检查本人做了什么、为什么、结果如何，以及证据的边界。

站点当前采用用户定义的四档参考。该规则是本库的编辑标准，不代表 OPM、Google 等来源的评分表，也尚未经过信度或效度验证。上下文不足时先追问或记录待核实点，不另设第五个分档：

| 档位 | 可观察表现 |
| --- | --- |
| 1 分 · 不通过 | 核心概念、基本事实或叙述无法成立；经历题说不清本人做过什么。经核实的故意造假属于不通过。 |
| 2 分 · 通过 | 基本概念和思路清楚，并能说明本人做过这件事，或能完成符合题意的合理推演。 |
| 3 分 · 优秀 | 有结构化复盘、实践亮点或高于岗位与级别常见要求的经验洞见。 |
| 4 分 · 卓越 | 达到行业领先水平的可度量结果，有证据支持并可归因到候选人的判断和行动。 |

每题的参考锚点结合该题观察信号解释；期望按岗位能力模型、级别和责任范围校准。通常以 2 分通过为基线；一两个维度达到 3 分优秀就有价值，4 分卓越应当少见。不能把四档合成对候选人的总印象；确认造假需要事实核验，叙述不一致本身不构成造假结论。

## 2. 晋升：能力表现、发展计划、组织机会需要区分

**事实。** GitLab明确区分职业辅导与晋升：前者帮助理解未来需要做什么，后者记录已经完成的贡献。其发展路径包含IC与管理分支，机会还取决于岗位需要，不能仅凭任职时间推定晋升。[GitLab：Engineering Career Development](https://handbook.gitlab.com/handbook/engineering/careers/)

**事实。** GitLab Staff页面列出领域技术领导、取舍、客户与业务理解、长期影响和复杂需求拆解，同时标注领导力与技术能力应参照当前Job Levels。该页是公司情境下的框架，不应照搬为普遍职级定义。[GitLab：Staff框架](https://handbook.gitlab.com/handbook/engineering/careers/matrix/staff/)

**建议。** 建立「能力领域 × 角色 × 影响范围」矩阵，而不是把高职级等同于更多冷知识。对同一系统设计题，初中级重可实现性，高级重质量与权衡，技术负责人重跨团队边界、演进及影响。面试强调有限时间内的新证据，晋升强调一段时间内可重复的表现；两者可共享能力模型，但不共享证据充分性要求。

## 3. 管理：一线带团队，二线通过经理改善多团队系统

**事实。** GitLab Engineering Manager职责涉及人员成长、招聘、项目计划、反馈、心理安全、交付和跨部门协调。[GitLab：Engineering Manager](https://handbook.gitlab.com/job-description-library/engineering/development/management/engineering-manager/)

**事实。** GitLab Senior Manager职责包含跨团队流程、经理辅导、经理1:1及skip-level沟通，其管理范围可包含多个工程团队。[GitLab：Engineering Leadership](https://handbook.gitlab.com/job-description-library/engineering/engineering-management/)

**建议。** 一线管理题围绕招聘、入职、目标、反馈、绩效、授权、团队健康与交付；二线围绕经理培养、组织边界、资源组合、继任、跨团队依赖和决策机制。要求分别说清直接干预、授权给经理的部分、监测信号和升级条件。不要用团队人数机械划分层级，也不要用个人救火数量代替管理效果。

## 4. 产品和工程结果：把发布后闭环纳入能力评价

**事实。** GitLab产品原则要求验证客户假设、设定成功指标，以产品和业务结果判断成功，而非仅统计发布。[GitLab：Product Principles](https://handbook.gitlab.com/handbook/product/product-principles/)

**事实。** DORA当前交付框架是五指标：变更前置时间、部署频率、失败部署恢复时间、变更失败率、部署返工率；建议按应用或服务情境使用，并警示把指标直接变成目标或依赖单一指标。[DORA：软件交付绩效指标](https://dora.dev/guides/dora-metrics/)

**建议。** 产品全链路题包含需求发现、问题验证、方案、交付、上线、采用、效果与后续调整。项目案例至少记录基线、观察窗口、结果指标、质量护栏、本人贡献与归因限制。没有实验或对照时，只能描述相关变化，不自动声称因果。DORA适合讨论团队交付系统，不应直接作为个人绩效排名。项目管理和技术规划题都要包含停止、降级或重新排序的条件。

## 5. AI时代：评价问题定义、生成物验证和系统约束

**事实。** Anthropic区分固定流程的workflow与由模型动态决定步骤的agent；其2024年文章建议从简单方案开始，并考虑延迟和成本。页面已注明工具生态变化，文章适合架构原则参考，不宜作为当前工具清单。[Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

**事实。** Anthropic的2026年agent评估文章区分过程记录与环境最终状态，结合代码、模型和人工评分；编码agent评价强调稳定环境、明确任务和测试，模型评分需要人工校准。[Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**建议。** 设置两类明确告知工具政策的练习：基础编码验证独立推理；允许AI的工程任务验证需求澄清、代码阅读、修改控制、测试、审查、结果解释和责任承担。不能把提示词熟练度或生成代码量直接当作能力。AI系统设计题补充检索质量、评估集、幻觉处理、权限与数据边界、工具失败、观测、成本、延迟及人工接管。各项是本库建议，不是上述来源的招聘要求。

可用一个具体任务贯穿：为客服知识检索系统提出方案 → 说明为什么不用更复杂agent → 给出离线及线上验证 → 处理错误引用和权限泄露 → 根据成本与质量证据决定下一步。既测判断，也测执行。

## 7. 跨岗位：产品与运营需要自己的专业证据

**事实。** 英国政府Digital and Data能力框架按角色及级别定义技能，可用于发展和招聘。产品经理包括用户洞察、价值与投入、生命周期、结果管理、产品领导和利益相关者管理；不能把它的政府职级直接映射为企业职级。[英国政府：Product manager](https://understand-digital-data-roles-skills.service.gov.uk/role/product-manager/)

**事实。** 其用户研究员框架把研究规划、设计与实施视为理解用户、影响服务及内容设计的工作，提供从入门到领导岗位的层级描述。[英国政府：User researcher](https://understand-digital-data-roles-skills.service.gov.uk/role/user-researcher/)

**事实。** GitLab营销项目管理岗位要求活动规划与执行、预算、全漏斗、跨职能协调及报告。[GitLab：Manager, Marketing Programs](https://handbook.gitlab.com/job-description-library/marketing/manager-marketing-programs/)。其社区项目岗位涵盖反馈、内容赋能、活动、持续参与和贡献者生命周期，并使用每月独立社区贡献者等指标。[GitLab：Developer Relations Program Manager](https://handbook.gitlab.com/job-description-library/marketing/devrel-program-manager/)

**事实。** GA4漏斗探索用于分析用户完成任务的步骤及流失，归因模型用于给转化路径中的触点分配信用；它们解决的分析问题不同。[Google：Funnel exploration](https://support.google.com/analytics/answer/9327974?hl=en)、[Google：Get started with attribution](https://support.google.com/analytics/answer/10596866?hl=en)

**事实。** Microsoft实验平台的第一手实践建议先明确假设、成功指标与适当随机化单位，并区分实验前、实验中和实验后阶段。[Microsoft Research：实验前设计](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-pre-experiment-stage/)

**建议。** 以上支持将Interview Compass扩展为跨岗位能力库：共享判断、执行、协作、学习和结果追问；专业题分别归属技术、产品、运营。技术基础及系统设计不是产品与运营岗位的默认必考项；按岗位实际需要选择技术理解、数据分析和AI工作流深度。不能用工程师评分锚点直接评价运营。

| 岗位或方向 | 专业能力 | 可评分证据与追问 |
| --- | --- | --- |
| 产品 | 用户研究、机会判断、产品策略、优先级、路线图、需求与体验、商业结果 | 用户分群与样本边界是什么？原始信息如何形成洞察？哪项需求未做？上线前后如何验证？如何区分用户价值和交付数量？ |
| 增长/用户运营 | 获客、激活、留存、转化、召回、用户分层及生命周期 | 漏斗分母、时间窗、队列和口径是什么？Top-k瓶颈如何排序？渠道变化、季节性和补贴如何影响结果？留存与成本护栏是什么？ |
| 内容运营 | 用户需求、选题、生产协作、分发、内容质量和转化闭环 | 内容服务谁、解决什么问题？怎样验证内容质量和有效触达？如何解释曝光、消费、行动之间的差距？AI生成内容如何审校？ |
| 社区运营 | 成员价值、参与与贡献、活动、规则治理、反馈闭环 | 如何定义健康参与而非刷量？贡献者是否持续？冲突如何处理？哪些反馈改变产品？如何归因社区与业务结果？ |
| 运营负责人 | 目标与资源、机制、跨职能项目、团队培养和组合取舍 | 如何把预算、人力和渠道约束转成计划？如何授权与跟踪？失败时停止什么、保留什么？怎样形成可复用机制？ |

**建议。** 对增长与实验题，要求候选人区分三种证据：描述性趋势、按模型分配的渠道信用、具有明确设计的增量效果。不能把归因工具输出直接当作因果证明。实验任务应明示假设、主指标、护栏、分流单位、样本与停止条件；社区场景还要解释成员之间的影响是否破坏独立性。运营没有实验条件时，应诚实说明比较对象、混杂因素及结论限度。

首批跨岗样例建议包括：产品「是否解决这个用户问题」、增长「激活下降诊断与行动」、内容「低转化内容计划」、社区「高活跃低贡献改进」。全部使用事实/Why/Top-k/执行/Next骨架，但提供不同评分锚点。产品评分观察洞察与取舍质量，运营评分观察组织实施、数据口径、复盘及持续结果，不能只评方案表达。

## 8. 对本仓库的落地建议

以下均为本库建议，不声称已经得到外部验证。

### 能力领域与证据

| 领域 | 应收集的证据 |
| --- | --- |
| 技术基础 | 概念推导、边界、反例、复杂度与故障机制 |
| 技术栈（含AI） | 适用条件、选型、集成、验证、升级与维护代价 |
| 工程化 | 测试、交付、质量、安全、可观测性和改善效果 |
| 项目管理 | 拆解、估算、依赖、风险、变化处理与交付闭环 |
| 技术规划 | 当前约束、选项、长期演进、资源、退出与迁移条件 |
| 协作、风险、失败 | 分歧、本人责任、处置、损失、反馈与机制变化 |
| 潜力、学习、韧性、自驱 | 新领域学习路径、反馈后变化、持续推进与主动求助 |
| 价值观与文化 | 具体行为、利益冲突和决策边界；避免性格及背景相似性判断 |
| 产品全链路 | 用户问题、结果指标、采用、质量护栏和上线后学习 |
| 一线/二线管理 | 团队或组织通过他人取得的持续结果与人员成长 |
| 领域建模（用户补充） | 业务概念与规则、商业化机制、数据粒度、特征口径、数据库映射和模型演进的产物与验证 |

领域建模在本轮研究完成后由用户补充，已由第 11 条需求重组为现行架构的 B 领域建模域；这里是项目设计要求，不声称上述公开框架已提供对应完整题库。

### 每题的统一追问骨架

1. **事实/证据**：约束、角色、本人行动、产物、结果及未知信息。
2. **Why**：为什么这样判断？候选方案、代价、被排除方案与当时可得信息。
3. **Top-k**：在给定资源下，最优先的2–3项是什么？排序依据与不做什么。
4. **执行**：如何拆分、验证、处理依赖、跟踪与纠偏？
5. **Next**：结果之后学到什么？下一步及改变判断的信号是什么？

「Top-k」在这里是优先级表达，不是算法题中的第k大元素，也不是强迫所有题目都有唯一前三名。事实题可精简模板；复杂项目题应保留判断与执行两条线，避免只会讲思路或只会堆工作量。

### 首批内容的优先级

建议先做可试评样例，而非立即铺满题库：研发侧包含编码/调试与系统设计；跨岗位包含项目复盘与管理情境；产品、运营分别包含专业实务任务。每组覆盖证据、追问、角色差异和评分锚点。总方案建议将这些纳入20题试点。用两位评价者独立评分后的分歧修改题目；再按实际覆盖缺口扩展主题和个人成长路径。

### 待验证点

- 各角色的维度权重、通过阈值与证据数量：公开框架不足以替本项目决定，需依据目标岗位和试评结果设置。
- 本地职级与GitLab角色名称的映射：不能直接等价。
- AI练习的工具政策、环境与评估集：应写入每个任务，随工具变化更新。
- 价值观与潜力的长期表现：单次访谈可能证据不足，宜增加工作样本、历史案例或持续观察。
- 当前网页会变更：后续内容落地记录引用日期；实质复用时再核验版本和许可。
