# Interview Compass 内容架构：能力主轴与正交入口

日期：2026-10-14。状态：重组方案。本文件替代“十一类并列”的现行分类设计；原十一类保留为需求来源和迁移映射，不再作为新站主目录。配套：[整体方案](./2026-10-14-interview-compass-redesign.md)、[补充框架研究](./2026-10-14-mece-framework-research.md)、[GitHub 样本研究](./2026-10-14-github-interview-research.md)。

## 1. 重组结论与 MECE 的适用范围

用八个能力域回答“主要考察什么”，用独立维度回答“涉及什么知识、面向什么岗位、在什么责任范围、用于什么场景、如何采集证据”。问题按主要评价目标唯一归属，其他关系作为索引。

这里的 MECE 是**内容组织和证据归类规则**：主归属唯一、需求覆盖完整、交叉关系显式。人的能力存在关联，一次真实工作可以同时体现多项能力；本方案不声称八域在心理学上相互独立，也不声称已证明所有岗位需求都被穷尽。

原分类混合了不同标准：计算机基础是知识；前端/产品/运营是岗位；工程化是技术与流程的集合；项目管理和规划是做事能力；一线/二线是责任与角色；失败是情境；Top K、Why 是提问方式。把它们继续并列，会不断出现重复和“其他”类。

采用多维模型有公开框架依据：SFIA 区分专业技能与责任等级，OPM 要求先定义岗位能力再设计结构化问题；但具体八域及其边界是本项目的编辑设计。[SFIA](https://sfia-online.org/en/about-sfia/how-sfia-works)、[OPM](https://www.opm.gov/policy-data-oversight/assessment-and-selection/structured-interviews/)

## 2. 八个能力域：以被评价的对象划界

| ID / 主目录 | 核心问题 | 子主题与典型产物 | 与相邻目录的边界 |
| --- | --- | --- | --- |
| A 专业解题与实现 | 能否用岗位专业知识设计、实现和验证一个解法？ | 原理推导、方法选择、编码与抽象、系统设计、专业分析与实验设计、质量/安全/性能验证；代码、设计、分析产物 | 业务语义与规则归 B；做不做及资源方向归 C；交付组织和持续运行归 D |
| B 业务理解与领域建模 | 能否准确表达业务对象、关系、规则及数据含义？ | 业务/产品/项目上下文、商业机制、概念/状态/事件、数据/特征模型、数据库映射、模型演进；词表、规则、模型与数据字典 | 技术机制与运行架构归 A；某投入是否值得归 C；不是泛泛“懂业务” |
| C 价值判断与方向规划 | 为什么做这件事，为什么现在做，怎样判断价值？ | 用户问题、业务价值、竞争/商业判断、指标与因果、ROI、优先级、不做清单、月季年规划；目标、方案取舍、路线图 | 业务关系是什么归 B；怎样按承诺交付归 D；人员与组织机制归 F |
| D 交付执行与持续运营 | 如何把目标变成可靠行动，并运行、纠偏、闭环？ | 任务拆解、估算、排期、依赖、容量、PMO、工程流程、发布与运营执行、观测、事故处置、风险与复盘动作；计划、运行记录、验收 | 解法本身正确性归 A；方向与投资选择归 C；处理关系与影响他人归 E |
| E 协作沟通与影响 | 如何使他人理解、协商、承诺并共同推进？ | 表达、信息同步、反馈、谈判、冲突、跨部门影响、预期与协作边界；沟通/决策记录和协作变化 | 持续招聘培养授权机制归 F；个人诚信和行为底线归 H；项目排期归 D |
| F 人才与组织建设 | 如何让团队与管理者持续产出，而非依赖个人补位？ | 招聘、培养、授权、绩效证据、团队结构、管理者体系、资源机制、继任与组织治理；人员成长及持续组织结果 | 一线/二线是角色与范围；一般交付归 D，方向归 C，临时协调归 E |
| G 学习适应与持续成长 | 面对未知、反馈与挫折，能力如何发生可验证的变化？ | 学习迁移、自我校准、自驱、恢复与求助、反思后的行为变化；前后对照、下一轮实践与复用 | 当场推理是否正确仍按 A/B/C 等评分；不凭一次表现给“潜力”人格标签 |
| H 职业责任与工作方式 | 如何守住事实、责任与底线，双方预期是否相容？ | 诚信、贡献归属、责任边界、职业判断、公平与数据伦理、不同意见、工作方式和职业动机；具体选择与预期 | 组织制度设计归 F；恢复能力归 G；文化匹配部分记录双方条件，不自动计作能力高低 |

专业解题涵盖不同岗位的专门方法，而不是只指编程。研发可以考代码/系统，产品可以考研究方法/原型验证，运营可以考渠道分析/实验，数据可以考统计/特征计算。它不能作为“凡与工作有关都放这里”的兜底目录。

拟定稳定能力键：A=`professional`，B=`domain-modeling`，C=`value-direction`，D=`delivery`，E=`collaboration`，F=`people-organization`，G=`learning-adaptation`，H=`work-responsibility`。题卡使用“域键.叶子能力”引用；首期先明确每个实际题目的叶子定义，不预先铺满未经试归类的能力树。

### 判断力、执行力、结构化思维的位置

它们保留为跨域的**观察提示**：判断力关注依据与取舍，执行力关注行动与纠偏，结构化思维关注分解和表达是否可检查，证据意识关注结论是否可复核。每题据此设计追问，但不默认对八域再叠加一套相同总分。

“产品/全链路思维”作为精选路径，主要串联 B 业务与模型、C 价值判断、D 执行闭环；“管理路径”串联 C/D/E/F/H；“成长潜力”主要观察 G，同时核对长期专业与协作证据。路径可以跨域，正文与评分目标仍有唯一归属。

## 3. 六类入口维度与管理轨道

| 维度 | 回答什么 | 示例 | 不能替代什么 |
| --- | --- | --- | --- |
| 主要能力 | 评价目标是什么 | domain-modeling.data-modeling、value-direction.prioritization、delivery.capacity-planning | 不等于知识主题或岗位 |
| 知识/方法主题 | 用到什么知识或工具 | OS、并发、数据库、React、AI/RAG、DevOps、用户研究、增长实验 | 不等于会用它取得结果 |
| 岗位 | 谁需要这类证据 | 研发、产品、运营、数据；前端/后端/客户端等专业方向 | 不直接决定高低职级 |
| 责任范围 | 为多大范围负责 | 任务、模块/项目、方向、团队、多团队、组织 | 不把规模大自动视为表现好 |
| 使用场景 | 为什么阅读或练习 | 求职、面试官评估、晋升、自查复盘 | 不等于题型 |
| 证据采集方式 | 怎样获得判断依据 | 知识解释、现场实操、设计、过去行为、假设情境、作品审查 | 不等于被考能力 |

另有**职业轨道**：专业贡献者、团队管理者、管理管理者，用于设置岗位要求。管理并非所有人的成长终点，资深专业贡献者也可以具有跨团队影响。业务领域如商业化、交易、内容、社区作为情境标签；AI 既可作为工程专业方向，也可作为任务工具条件，不作为新责任等级。

校招是受众/招聘入口：允许课程、社团、开源或小型构造案例；不能把“校招”与“二线管理”并列成所有人必经的一条等级序列。现有阶段入口改为“校招准备”与“按责任范围准备”两类导航。所有维度由受控词表维护，不无限生成标签组合页。

## 4. 原十一类的完整迁移映射

| 用户原始需求 | 新归属 | 保留方式 |
| --- | --- | --- |
| 1 计算机基础 | A + 知识主题 | 算法、OS、组成、编译、网络、数据库、并发、分布式全部保留；学习指南链接相应题卡 |
| 2 职能技术栈，含 AI；产品、运营专业 | A + 岗位/专业方向/主题 | 前后客户端、语言框架、产品方法、运营方法、AI 工程；版本是内容适用条件 |
| 3 工程化、基础设施、流程、DevOps、微服务/微前端/monorepo/子仓库 | A / D | 方案机制和实现归 A；交付流程、仓库协作、发布运行归 D；按主问拆分 |
| 4 项目管理、排期、资源调度、PMO | D；方向取舍 C；关系协调 E | 保留项目管理路径；分别记录排期、选择与沟通证据 |
| 5 月度/季度/年度技术规划 | C | 同时适用于产品/运营方向；执行跟踪链接 D |
| 6 协作、风险、失败项目 | E / D；学习变化 G | 冲突沟通归 E，风险/止损归 D；失败是情境标签，不单独成为能力 |
| 7 结构化、学习、自驱、韧性与持续成长 | G + 跨域观察 | 学习与恢复归 G；结构化推理按具体任务评价，不只放在“潜力”类 |
| 8 人的素质与文化匹配 | H + 双向预期记录 | 工作相关行为与诚信保留；文化相容性不等于相似性或优劣排名 |
| 9 产品/全链路、结果、商业意识 | B / C / D | 独立精选入口仍保留，分别指向业务语义、价值判断、交付后的验证 |
| 10 一线/二线管理 | F + 管理轨道/范围，并串联 C/D/E/H | 分别检验团队持续产出与管理者/多团队机制，不以题目难度递增代替角色差异 |
| 11 领域模型、商业化、数据/特征、数据库映射 | B | 为独立一级能力域；商业决策 C、物理性能 A 交叉引用 |
| 编码、代码抽象、系统设计 | A；业务抽象 B | 代码抽象与业务模型分别评价，不能用设计术语掩盖编码正确性 |
| 问题拆解、判断力、执行力 | 跨域观察；价值判断 C，交付执行 D | 为各题增加可观察动作与依据；不建立重复总分 |
| 过去事实、Why、Next、Top K、最成功/失败、离职与下一份期待 | 提问方法/情境；H 动机与预期 | 按主问选择能力归属；保持完整事实与责任链 |

## 5. 域之间容易混淆的判定规则

**先看主要评价目标，再看题目谈论的对象。** 同样讨论数据库，事务机制推导归 A，订单数据关系归 B；同样讨论活动，收益优先级归 C，排期与异常处理归 D。

| 相同题面下的不同主问 | 主要归属 | 判定依据 |
| --- | --- | --- |
| 订单为何与支付、退款分开建模？ | B | 业务语义、基数、身份与规则 |
| 上述模型在高并发下怎样保持约束？ | A | 技术实现、正确性、故障与验证 |
| 分成规则变化后怎样保留历史计算？ | B | 版本、时间语义及可追溯性 |
| 如何安排回填、灰度与回退？ | D | 实施顺序、依赖、执行和风险 |
| 推理优化与新功能只能投一个，选哪个？ | C | 价值、机会成本与目标 |
| 已选定方向但两个团队没有空档，怎样排期？ | D | 容量、依赖及承诺 |
| 两团队意见不同，怎样谈成新的承诺？ | E | 信息、谈判、冲突与协作变化 |
| 如何建立长期容量分配和决策权机制？ | F | 持续组织机制，而非一次协调 |
| 留存上涨如何判断是活动的净增量？ | C | 结果有效性、归因及商业判断 |
| 如何正确设计分流、样本量与统计检验？ | A | 专业方法与技术正确性 |
| 一次判断错误之后具体改变了什么？ | G | 可验证的学习与后续行为变化 |
| 压力下是否承认错误、隐瞒风险或冒领成果？ | H | 诚信、责任与行为边界 |

数据/特征模型在 B；特征计算和工程实现性能在 A；上线与运行在 D。一个案例涉及三域时可以拆成三道有不同主问的题，全部引用同一案例。

## 6. 内容形态与唯一归属

内容分为：知识指南（概念与资料索引）、题目卡（主问、证据锚点与评估参考）、案例卡（事实与产物）、准备/评估指南（使用方法）。知识指南不冒充已完成题，案例不因出现在多个入口复制全文。

每道题遵循以下规则：

1. `primaryCapability` 必须是一个明确叶子能力；题目评估只针对该目标。
2. 可以列少量 `secondaryCapabilities`，但要有独立证据依据；题单统计按主归属去重。
3. 主题、岗位、范围等多值索引不会产生第二份正文。题目 ID 不随主目录变化而改变。
4. 无法唯一确定主目标，先重写主问；若实际上是多段任务，拆为独立题卡，共享案例。
5. 因知识不足而影响表现与被考能力缺口分别记录；未知/未观察与低表现分开。
6. 每份岗位题单明确选哪些能力、为什么、用什么证据，不要求所有岗位按相同权重考八域。

示例（拟定字段，不是已实现 schema）：

```yaml
id: pricing-model-history
kind: question
title: 分成规则变化后，旧交易如何重现原来的结算？
primaryCapability: domain-modeling.model-evolution
secondaryCapabilities: [professional.implementation]
topics: [commercialization, data-modeling, database]
roles: [engineering, product, data]
responsibilityScopes: [project, direction]
careerTracks: [individual-contributor]
scenarios: [interview, promotion]
format: design
toolPolicy: optional-ai-with-disclosure
status: reviewed
```

主要证据是模型如何表达历史规则；辅助证据才是实现。若主问换成“零停机发布新规则”，应另建 D 类执行题。AI 可用、限用或禁用写入任务条件，不通过岗位名称猜测。

## 7. 岗位入口如何由同一题库生成

| 示例入口 | 选择的能力与证据重点 | 使用范围 |
| --- | --- | --- |
| 校招研发 | A 原理/编码/调试，B 小模型，D 小任务闭环，G 学习，H 诚信 | 课程与小项目即可；没有管理经验不扣分 |
| 产品经理 | B 用户/商业概念，C 问题价值与规划，A 研究/验证方法，D 推进，E 影响 | 产品专业题单，领域模型深度按真实岗位选择 |
| 增长/内容/社区运营 | A 专业分析与方法，B 人群/生命周期/供需语义，C 净收益，D 策略执行，E 协作 | 不把品牌增长题视为全部运营题 |
| AI 工程师 | A 编码/系统/评估实现，B 数据/特征/权限语义，C 投入价值，D 运行与失败处理 | 同时声明工具政策；不只考提示词与名词 |
| 一线管理 | F 培养/授权/反馈，C 目标，D 团队交付，E 协作，H 责任 | 管理轨道、团队范围；按实际职能加专业题 |
| 二线管理 | F 负责人/组织/继任，C 方向组合，D 多团队运行，E 决策沟通，H 底线 | 通过管理者形成持续结果，不能只以救火数量评分 |
| 晋升自查 | 根据目标角色/范围选择上述能力，收集跨周期的持续证据 | 面试单次表现与晋升长期表现不等量 |

这是题单设计起点，不是规定所有岗位必须考同一组合。管理专业能力与 IC 影响力分开；岗位业务缺口、实际责任和当前证据决定取舍。

## 8. MECE 自查与试点

本轮完成的是结构设计，不是题库全量归类或评分有效性试验。用原十一类与补充要求做覆盖检查；用第 5 节十二个易混题面做边界演练，检查是否存在同一主要证据被重复评价。

首批仍为 20 题：A 5、B 3、C 3、D 3、E 2、F 2、G 1、H 1。其中同时覆盖研发/AI、产品、运营及一线/二线管理；B 明确包含商业规则、数据/特征口径、持久化映射。数量用于验证分类，不代表正式权重。完成后检查：

- 每题有且仅有一个主要叶子目标，能说明为什么不归邻近类别。
- 原始需求均有主题/能力/入口去向，不能以“其他”目录掩盖缺口。
- 独立评价者能理解归类，分歧有记录；这属于后续试点验收，本轮尚未实施。
- 换岗位或责任范围后，只改变题单和证据要求，不复制题目正文；四档评估按岗位、能力模型、级别和责任范围校准。
- 回答事实与评估依据分开；证据不足时继续询问，不自动归为不通过；文化相容性和能力表现分别记录。
- 四档为 1 分不通过、2 分通过、3 分优秀、4 分卓越；一两个维度达到优秀就有价值，卓越要求行业领先、可度量且可归因的结果，不合并成候选人总分。

如果后续出现无法归类的新内容，先判断它是新能力、主题、角色、情境还是方法；只有现有能力域确实无法表达新的主要评价目标，才扩展一级分类。
