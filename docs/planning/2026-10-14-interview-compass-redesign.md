## 1. 目标与本次需求记录

Interview Compass 让读者按岗位或主题自由探索问题。问题是核心内容；每题解释它想探查什么，以及读者可以继续查哪些知识。站点不代替读者作答，也不替面试官给人打分。覆盖研发、AI 工程、产品、运营及管理等方向。

用户这次明确提出的内容，应完整保留：

1. 计算机基础：数据结构、操作系统、组成原理、编译、网络、数据库，以及并发、分布式。
2. 职能技术栈：前端、后端、客户端、语言和框架，新旧技术演进；加入 AI 工程、适配及实际应用。
3. 工程化：基础设施、开发流程、DevOps、微服务、微前端、monorepo、多仓库及子仓库管理。
4. 项目管理：排期、冲突、资源调度、依赖、PMO。
5. 技术规划：月度、季度、年度方向与资源安排。
6. 协作与软素质：合作、风险、失败项目及后续处理。
7. 个人潜力：结构化思维、学习能力、韧性与恢复、自驱和持续成长。
8. 工作价值观与组织文化：个人行为与公司、项目工作方式的相容性。
9. 产品与全链路思维：从问题到目标、行动，再到可度量结果；独立成类。
10. 管理：一线管理、二线管理及进阶的组织建设。
11. 领域建模能力：业务、产品和项目认知，商业化机制、数据模型、特征模型，以及领域概念到数据库模型的映射。

此外，必须显式覆盖校招、基本编码、代码抽象、系统设计、问题拆解、执行力和判断力；增加产品面试、运营面试的专业内容。核心提问方法是过去事实、为什么、以后怎么做，以及不同尺度的 Top K / 不做清单。

本方案采用的默认假设：公开中文内容优先；保留 Interview Compass 名称和当前独立仓库；首期不依赖账号和后台服务；完整旧内容迁移及大规模外部资料整理留到后续分批执行。用户尚未指定首发岗位权重、域名或截止日期，以下排期是交付顺序，不是时间承诺。

## 2. 项目现状与真正要改的地方

现有项目已具备基础、前端题库、框架、系统设计、团队管理与成长素材。`docs/guide/foundation.md` 有计算机基础提纲；`docs/team/Stages.md` 有成长阶段；`docs/team/Team.md` 有团队管理题；`docs/Collection/OftenAsked.md` 已有离职原因、项目、优势和规划等行为题。因此应继承内容与作者贡献。

主要问题：

| 现状 | 影响 | 重构方向 |
| --- | --- | --- |
| 根 README、guide 与 Collection 同时承载提纲和正文 | 更新分散，题目与解答关系不稳定 | 每道题一个权威内容文件，入口从元数据生成 |

本轮基于源码审查，不声称旧站不能构建；没有运行旧依赖安装或生产部署。

## 3. 内容架构：八个能力域，正交入口

一级目录统一回答“主要考察什么能力”。每道题按主要评价目标唯一归属；知识主题、岗位、责任范围、使用场景和证据采集方式单独维护。MECE 用于归类和覆盖检查，不意味着现实中的能力相互独立。完整边界与原十一类映射见[内容架构](./2026-10-14-content-architecture-mece.md)。

| ID / 主目录 | 主要评价对象 | 代表证据 |
| --- | --- | --- |
| A 专业解题与实现 | 原理、专业方法、设计、实现及验证 | 推导、代码、设计、调试与专业分析 |
| B 业务理解与领域建模 | 概念、规则、状态、关系与数据语义 | 业务/商业规则、领域/数据/特征模型、数据库映射 |
| C 价值判断与方向规划 | 用户价值、结果口径、取舍及方向 | 优先级、不做清单、ROI、月季年规划及依据 |
| D 交付执行与持续运营 | 目标如何转成行动、运行与纠偏 | 排期、容量、依赖、风险、交付/运营记录与验收 |
| E 协作沟通与影响 | 信息、分歧与承诺如何共同推进 | 沟通、谈判、跨部门影响与协作变化 |
| F 人才与组织建设 | 通过人才和组织形成持续结果 | 招聘、培养、授权、管理者体系、治理与继任 |
| G 学习适应与持续成长 | 能力如何在未知、反馈和挫折后改变 | 学习迁移、恢复、自驱、行为前后变化 |
| H 职业责任与工作方式 | 工作相关行为与双方预期 | 诚信、责任、底线、动机与具体工作约定 |

工程化拆分为 A 的技术机制/设计和 D 的交付运行；产品与全链路入口串联 B/C/D；管理入口串联 C/D/E/F/H。领域建模独立保留在 B，不压缩成数据库机制或泛业务理解。判断力、执行力、结构化与证据意识为跨域观察提示，不重复建立总分。

### 岗位与专业入口

研发包含前端、后端、客户端、平台/基础设施、测试与质量；数据作为独立岗位入口；产品与运营有自己的实务题。AI 工程是研发专业方向，也可以是其他岗位的工具/知识主题。产品研究和运营实验等专业方法归 A，业务语义归 B，价值判断归 C，执行闭环归 D。

管理是职业轨道与专题入口：团队管理者和管理管理者分别准备，专业贡献者不被要求转入管理。产品全链路作为独立精选路径继续保留，不复制一份题库。

### 责任范围、场景与采证方式

责任范围：任务、模块/项目、方向、团队、多团队、组织；按实际目标设置要求，不直接对应公司职级。校招单独作为准备入口，允许课程、社团、开源和小项目事实，不作为从校招到二线管理的一条必经等级序列。

使用场景：求职准备、面试官评估、晋升自查、日常复盘。采证方式：知识解释、现场实操、设计、过去行为、假设情境、作品审查。知识指南、题目卡、案例卡和方法指南是不同内容形态；只有完整题卡计入题库完成数。

例如“运营 → 项目范围 → 晋升自查”从同一内容集合选出专业分析、数据口径、策略取舍、执行闭环和协作题；文化相容性记录双方条件，不自动作为能力高低排名。

## 4. 贯穿所有题目的判断方法

统一使用这条证据链：

**背景与目标 → 个人责任 → 问题与约束 → 备选方案 → 判断与取舍 → 行动及协作 → 结果与证据 → 复盘 → 下一步。**

这是本项目对已有博客思想的整理，不声称它是外部统一标准。STAR 可以帮助叙述，但本项目更强调决策依据、归因边界、失败与后续验证。

### 核心问题必须保留

| 问题组 | 主问与追问 | 要判断的内容 |
| --- | --- | --- |
| 离开与选择 | 为什么离开？下一份工作需要得到什么？曾尝试改善什么？有哪些不能妥协的条件？ | 动机、边界、自我认知、双方预期 |
| 最好的事 | 哪件事最好？为什么按这个口径最好？个人贡献是什么？结果如何核验？ | 价值判断、责任、结果意识 |
| 失败的事 | 哪件事失败？当时有哪些已知信号？为什么那样选择？如何止损、恢复、避免重演？ | 校准、责任、恢复与学习 |
| Why / Next | 为什么不是其他解法？重做会怎么改？什么新事实会改变你的判断？ | 替代方案、迁移、可调整性 |
| Top K / 不做 | 技术、业务、产品、战略或具体实现里最重要三项与应暂缓三项是什么？ | 判断口径、机会成本、尺度切换 |
| 判断力 | 信息不足时如何决定？如何区分事实、假设、偏好？什么时候求助、升级、停止？ | 决策质量与边界 |
| 执行力 | 怎样从目标拆到下一步？谁负责？如何发现阻塞？什么时候交付并验证？ | 推进、反馈、闭环 |
| 问题拆解 | 对一个模糊请求先澄清什么？如何定位关键约束？如何验证最不确定的一段？ | 建模、分解、验证顺序 |

Top K 必须说明排序对象、时间范围与收益/成本/风险口径；“最不重要”改写为“此刻可暂缓、删除、外包或替代”，避免把过去投入脱离当时条件作评价。

“把劣势变成可提升的角度”应体现为诚实说明短板、后果、改进动作及后续证据；缺点仍是缺点，不改写成虚假的优点。

### 问题边界

题卡要让读者知道为什么问、可能在观察什么、适用于哪些岗位或情境。它可以给出启发式追问、反思角度和值得查阅的背景知识，但不提供示范答案、回答套路、表现等级或招聘结论。关于公平、岗位相关性和避免文化偏见的研究，可用于解释题目边界；不因此在站点加入评分系统。

## 5. 题目卡与案例卡

每道公开题至少包含：稳定 ID、题目、考察目的、主要能力、主题、适用岗位或情境、来源/更新时间。情境、追问、相关背景知识和延伸阅读按需提供。题目可以是开放的启发，不要求答案、回答组织模板、评分锚点或评价结论。

建议元数据示例（字段契约在实施时验证）：

```yaml

id: planning-priority-under-capacity

roles: [engineering, product, operations]
responsibilityScopes: [direction, team]
careerTracks: [individual-contributor, team-manager]
scenarios: [interview, promotion]

observationPrompts: [judgment, execution, problem-framing, outcome]

reviewedAt: 2026-10-14
sources:
  - url: https://liyuk.com/writing/2025/11/technical-planning-business-and-competitive-analysis/
    usage: adapted
```

可选的题目补充包括场景设定、追问、可能观察的信号、延伸知识与来源。这些是帮助读者思考的材料，不是答案模板或评分表。内容完成度以题目表达清楚、目的可理解、分类与来源可信为准；无需为每题强制编造案例或追问树。

## 6. 特别补齐的内容

### 领域建模：从理解业务到表达规则与映射数据

本项目将“领域建模能力”定义为：在业务、产品和项目上下文中，识别概念、参与者、关系、规则、状态、事件与边界，并将其表达为可沟通、可验证、可演进的模型。数据库建模是其中一段；不要求候选人必须使用 DDD 术语或某种固定方法。

| 子能力 | 观察内容 | 可要求的产物或证据 |
| --- | --- | --- |
| 业务、产品与项目认知 | 谁参与，解决什么问题，上下游是什么，项目负责哪段，规则来自哪里 | 参与者/流程/责任边界图、概念词表、假设清单 |
| 商业化建模 | 谁使用、谁付费、为谁创造价值；定价、计费、成本、补贴、退款、分成与结算如何关联 | 收费与资金流、计算规则、收入/交易额口径及例外场景 |
| 领域概念与规则 | 实体身份、关系、生命周期、状态转换、事件、必须始终满足的约束 | 概念模型、状态图、规则与异常用例；同词异义和不同上下文的映射 |
| 数据模型 | 数据粒度、标识、基数、来源、所有者、历史版本与派生口径 | 逻辑数据模型、数据字典、来源与变换链路 |
| 特征模型 | 特征描述谁/什么、用于什么判断、从哪些数据按什么时间窗派生、何时可用 | 特征定义、计算口径、更新与缺失策略、线上/离线一致性验证；预测任务的泄漏检查 |
| 数据库存储映射 | 领域概念与表/文档/事件如何对应，约束、查询、事务和历史追溯如何落地 | ER 图或等价模型、schema、约束、查询样例及迁移方案 |
| 模型演进 | 新业务、规则变更、旧数据与不同版本如何共存，谁判断兼容与修正 | 变更影响、回填、兼容策略、校验和发布后的反馈 |

这里的“特征模型”默认指数据/算法/AI 场景中，用于描述、分群、预测或决策的特征及其派生规则。若以后讨论的是产品功能组合及可变性模型，单列子主题，避免同名混用。

与相邻能力的边界：产品与全链路思维关注“问题是否值得解决、怎样证明有价值”；领域建模关注“业务对象、规则及关系是什么，如何准确表达”；系统设计关注“模型如何在系统中运行，满足规模、质量与成本约束”；数据库基础关注存储机制。一个案例可以覆盖这四项，但评价证据分别记录。

建议首题使用明确标注的构造案例：**为一个可购买多件商品、部分退款、平台补贴和商家分成的平台建立模型。** 先澄清业务规则，不预设唯一 schema，再依次追问：

1. 谁是用户、买家、付款人、商家与结算接收方？哪些角色可由同一主体承担？
2. 订单、订单项、支付、退款和结算是否分别有身份与生命周期？为什么？
3. 同一订单分批支付或部分退款时，必须保持哪些金额和状态约束？
4. 成交额、实际支付、平台收入与商家应收如何定义？平台补贴由谁承担？
5. 分成规则变化后，旧交易如何重现当时的计算，而不是被新规则重算？
6. 产品、运营和研发使用的“成交用户”是否同一口径？差异如何显式表示？
7. 如果做“复购倾向”特征，粒度、窗口和预测时可得信息是什么？如何避免使用未来数据？
8. 模型怎样映射到数据库？哪些约束由数据库、应用或核对流程保障？发生重复事件或迁移错误如何定位？

这类问题的考察意图可以提示读者关注：概念和规则如何表达、例外与历史如何处理，以及模型如何对应数据实现。面向产品/运营时可以多看规则、商业机制与口径；面向研发时可以延伸到约束和持久化；面向数据/AI 时可以延伸到特征时间语义与可用性。校招读者可以用小型构造情境思考，不要求有商业化大项目经历。

### 编码、抽象、系统设计是不同证据

基本编码看正确性、边界与可运行验证；代码抽象看接口、状态、职责和变化点；系统设计看目标、规模假设、故障、成本、数据与演进。问题拆解贯穿三个层次。另加调试/定位题，观察假设如何被运行证据验证。

AI 辅助与非辅助任务分别注明规则。允许 AI 的题要看需求澄清、上下文、改动审查、错误定位、验证与结果，而不是只看生成速度；基础机制仍要独立解释。面试材料中明确哪些代码/判断来自工具、哪些经过本人验证。

### 产品与运营的首期专业题

产品：模糊需求如何变成用户问题；为什么不做某功能；如何验证原型；指标上涨但用户投诉增加怎么办；路线图遇到战略变化怎样改；一个失败功能如何复盘。

运营：流量上涨但留存下降怎么诊断；活动带来的增长是增量还是补贴套利；社区内容供给下降怎么拆解；渠道投放如何同时看短期成本和后续留存；商家供给与用户需求错配怎么处理；活动执行发生异常如何止损。

要求说明人群、周期、分母、对照、季节性、渠道变化及自身贡献，避免把一次曝光、GMV 或完成率直接当作长期价值。

### 一线与二线管理

一线：目标与容量、团队判断、交付可预期、授权、反馈、绩效证据、培养、招聘、冲突与可持续工作节奏。

二线：是否需要增加管理层；团队边界；管理者选拔培养；目标组合与资源配置；跨团队决策；继任；信息机制；治理底线；组织结果能否在本人不在场时持续。

管理题与项目管理区分：排好一个项目不等于持续建设团队，带好一个团队不等于建立多团队机制。晋升问题可以引导读者回看跨周期的责任与成长事实，但站点不替组织做晋升判断。

## 7. 内容来源和迁移

优先顺序：当前项目作者内容 → 本地博客已公开文章 → 个人旧资料的可公开观点 → 第一手标准与文档 → 作者维护的公开题库 → 二手资料线索。

博客中已找到可直接支撑本方案的总纲、校招、产品判断、Top K、规划、潜力、一二线管理系列。具体映射见来源清单。文章正文与题卡各有用途：从文章提炼可追问的问题，保留原文链接，避免全篇复制后换一个标题。

博客迁移目录记录了仓库外旧材料和旧站 tag。它同时说明部分内部题库、公司案例和近期规划不能原样公开。因此后续旧资料迁移先分“可直接整理、需改写、只提炼原则、保留私有”；首期优先使用现有公开版。这里只登记来源，不把内部原文放进公开仓库。

旧项目按文件和文件内题目两个层次盘点：

| 旧位置 | 新去向 | 处理 |
| --- | --- | --- |
| guide/foundation | A + 计算机基础知识主题 | 补数据库、并发、分布式，拆题并核验 |
| guide/basic、advanced、framework 和 Collection | 按主目标分到 A/B/C/D；保留岗位/主题索引 | 按主题拆分，去重，标注版本 |
| guide/architecture 与 System Design 提纲 | A 的系统设计；业务模型指向 B | 增加约束、异常、取舍、验证 |
| team/Stages | 责任范围、职业轨道与晋升入口 | 保留历史观点，重写责任范围 |
| team/Team | F 人才与组织；链接 C/D/E | 从泛谈改成情境、追问和证据 |
| Collection/OftenAsked | 按主目标分到 E/G/H/C 等域及求职入口 | 拆开行为题、知识题；清理重复标题和重复问题 |
| README 与 guide 索引 | 首页、能力页、岗位页 | 不再维护完整重复题单 |

维护 migration manifest：来源文件/锚点、作者、目标 ID、内容动作、旧 URL、新 URL、资产、来源许可、复核状态。区分原始 Markdown 路径与真正旧站 URL；旧锚点需依据旧 HTML 实际核验，不能凭标题猜测。

外部资料只提炼结构与问题，逐条引用；允许转载的内容遵循许可证和署名要求。仓库已有多人贡献，保留归属；package.json 的 ISC 标记不能自动证明所有第三方图文都适用同一许可。skills 可提供任务执行与审核方法，不直接当作岗位能力或面试标准。

## 8. 站点方案摘要

用户已确认采用 Astro + Starlight，GitHub Actions 构建并部署到 GitHub Pages。Markdown 内容集合保存唯一题目；Astro 生成岗位、主题、能力、责任范围和面试/晋升场景入口；Pagefind 负责中文全文搜索。Radix Themes 作为全站视觉与控件基线，Radix Primitives 用于可访问的交互；Starlight 主题映射到同一套 token。详细边界见[技术方案](./2026-10-14-site-and-deployment.md)。

首页优先提供直接搜索和主题浏览，同时保留开放的岗位探索，不指定单一主读者。题目详情突出题目本身和考察意图；相关追问、情境、背景知识按需出现，不加入答案、评分或招聘建议。
