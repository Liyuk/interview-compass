# Interview Compass：1,500 题 MECE 扩充蓝图

日期：2026-10-15。当前题库：1,067 道中英配对题。目标：1,500 道，即新增 433 道原创双语题。本文先定能力边界、模块目标量和岗位覆盖，再按四批串行扩题；本轮不做语义近似题合并。

## 一、分类原则

题目只有一个 `primaryCapability`，表示这道题最终要判断的主要能力；知识主题、岗位、责任范围、职业轨道、使用场景和题型是可交叉组合的独立入口，不复制题目，也不与 A–H 能力域混作同一层级。跨域经历可以拆成不同主问，不因共享同一个案例而重复评价同一目标。

MECE 在这里指“题目归档主目标唯一、已声明的能力范围有入口”，不表示人的能力彼此独立，也不保证这八类是心理测量学量表。归类时先问：这题最终需要读者判断什么？再用相邻叶子边界决定主归属。

## 五、扩题批次与质量闸门

按模块边界分四批顺序完成，不并行生成：

1. A + B：126 道，先补专业工作主干与领域模型差距。
2. C + D：119 道，补方向判断到交付闭环。
3. E + F：108 道，补协作影响及两级管理/人才组织能力。
4. G + H：80 道，补学习成长、韧性与职业责任。

每道题拥有稳定 ID、唯一主能力、明确问题对象、双语题面、可观察意图和信号；语言文件的标签和主归属完全一致。每道题记录岗位、主题、责任范围、职业轨道、场景和题型，不用 `其他` 替代已有分类。每批更新来源台账并运行内容校验、单元测试、类型检查及题量报告。

本轮保留逐字重复校验，防止同一题面/ID 重复；不运行或处理语义近似项合并。到达 1,500 后，再另行进行串行语义去重和归类复核，合并时保留有用信号、追问和来源。

## 六、GitHub Actions 负载与触发策略

仓库当前的 Pages 流水线每次完整运行包含依赖安装、Chromium 安装、Astro 类型/内容检查、单元测试、双语站点构建、Pagefind 索引和 E2E。Playwright 有 33 条测试定义、桌面 Chromium 与移动端 Chromium 两个项目，共约 66 个测试执行，限制为 2 个 worker。最近一次 PR 检查总计约 94 秒，其中浏览器安装约 21 秒，`npm run ci` 约 57 秒；同一提交的 `push` 检查约 97 秒。`main` 推送的构建约 106 秒，随后 Pages 部署约 48 秒。

原工作流对所有分支都监听 `push`，同时监听 `pull_request`。PR 分支推送因此会为同一提交启动两份完整检查，且 `github.ref` 不同，现有并发组不会相互取消。工作流现已限制为：所有 PR 仍完整检查；只有 `main` 的 push 完整检查并部署；`workflow_dispatch` 保留手动运行入口。这样避免 PR 分支重复消耗 runner 时间，同时保留合并前检查和主分支部署门禁。

从 1,067 题增到 1,500 题，题目 Markdown 文件从约 2,134 个增至约 3,000 个（中英文各一份，增加约 41%）。内容校验、静态页面生成和 Pagefind 索引会线性增加工作量，但当前体量很小，预计不需要拆成多套 CI 或取消 E2E。题量报告不属于每次发布所必需的质量门禁，可在每批扩题后本地运行并检查报告。先保持现有完整 CI，把重复触发消除；若后续实测构建时间明显增长，再按数据优化浏览器安装缓存或检查并行度。
