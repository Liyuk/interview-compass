title: How do you govern consistency and exceptions as multiple teams extend a design system?
question: >-
  After several product teams adopt a design system, some begin copying components and adding local
  variants, making similar features increasingly inconsistent. How would you decide which
  differences merit becoming system capabilities and which should return to shared patterns, and how
  would you create governance that teams can sustain together?
intent: >-
  Assesses whether the candidate can operate a design system as a cross-team product, balancing
  standardization benefits, local needs, and long-term maintenance cost.
signals:
  - >-
    Uses recurring contexts, user impact, and maintenance cost to decide what belongs in the shared
    system
  - >-
    Defines conditions, ownership, and review points for exceptions instead of allowing variants to
    grow without limits
  - >-
    Establishes sustainable contribution, review, release communication, and adoption-feedback
    practices
